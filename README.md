# 신호판 대시보드

[`SIGNAL_APP_SPEC.md`](SIGNAL_APP_SPEC.md)의 무릎매수(v2)/어깨매도(참고) 시그널 로직을 기반으로,
종목을 자유롭게 추가·변경·제거하면서 현재 시그널 상태와 히스토리, 리밸런싱 상태를 확인하는
개인용 참고 대시보드.

화면에는 스펙의 이름 대신 **매수 시그널 / 매도 시그널**로 적습니다. 조건이 여러 갈래여도
사람이 볼 때 알아야 하는 건 결국 사라는 건지 팔라는 건지이기 때문입니다. 코드와 API의
필드 이름(`knee_buy_v2`, `shoulder_sell_ref`)은 스펙과 1:1로 맞춰 그대로 둡니다.

앞으로의 방향(다중 사용자·배포·PWA)과 그 순서는 [`ROADMAP.md`](ROADMAP.md)에 있습니다.
새 테이블을 만들기 전에 거기 있는 **공용/사용자별 경계 표**를 먼저 보세요.

## 구조

- `backend/` — FastAPI + SQLAlchemy. 지표 계산, 시그널 판정, 매수 워크플로우, 리밸런싱/비중조절 신호, yfinance 데이터 수집.
  빌드된 화면도 여기서 함께 내보냅니다(`app/web.py`) — 띄울 프로세스가 하나뿐입니다.
- `backend/migrations/` — Alembic 리비전. 스키마가 바뀌는 길은 여기 하나입니다.
- `frontend/` — Vite + React + TypeScript. 대시보드/히스토리 차트/리밸런싱/종목 관리 4개 화면.
  폰에 설치해 앱처럼 쓸 수 있습니다(`public/manifest.webmanifest`, `public/sw.js`) — 아래 "폰에 설치해서 쓰기".
- `Dockerfile` / `docker-compose.yml` / `Caddyfile` — 서버에 올릴 때. 개인 PC에는 필요 없습니다.
- [`DEPLOY.md`](DEPLOY.md) — **서버에 올리는 절차.** 오라클 인스턴스 만들기부터
  도메인·HTTPS·첫 배포까지, 막히는 자리(방화벽 두 겹)를 포함해 순서대로.
- [`SIGNAL_APP_SPEC.md`](SIGNAL_APP_SPEC.md) — **시그널이 무엇인지.** 지표 공식, 조건식,
  경계값, 매수·리밸런싱 규칙. 조건식을 바꾸려면 여기부터 고칩니다.

DB는 개인 PC에서 SQLite 파일 하나, 서버에서 Postgres입니다. 코드는 같고 `DATABASE_URL`만 다릅니다.

## 화면 구성

- **대시보드** — 상단 요약 카드(신호등 현황 / 다음 리뷰 / 비중조절 신호 / 포트폴리오 배분 — 현금과
  평가손익 포함), 구분·신호 필터 칩, 그리고 종목별 시그널 매트릭스(맨 끝 칸은 **마지막 매수 시그널
  날짜**). **표에서는 한 칸이 한 줄**입니다 — 값 하나와
  조건 충족 기호(✓ / · / ?) 하나. 조건이 무엇인지는 **열 머리글에 한 번만** 적습니다(`매수 조건 < 0`).
  조건은 그 열의 성질이지 행마다 달라지는 값이 아니고, 행마다 반복하면 다섯 종목에 화면이 다 찹니다.
  해석 문구("MA20 하회", "추세 없음")는 마우스를 올리면 나오고, **카드 보기**에는 그대로 다 적혀 있습니다.
  종목 이름은 국내는 **종목명**, 해외는 **티커**로 적고, 누르면 **차트가 팝업으로** 뜹니다 —
  보던 표의 스크롤과 필터를 잃지 않습니다.
  좁은 화면에서는 카드 보기로 자동 전환되며 상단에서 직접 전환할 수도 있습니다.
  맨 앞의 **⠿를 끌어서** 순서를 바꾸고(키보드는 ↑↓), 상단 **설정**을 누르면 보던 표가 그대로
  입력칸으로 바뀌어 여러 종목을 고친 뒤 한 번에 저장합니다. 순서는 저장되어 리밸런싱·히스토리
  화면에도 그대로 적용됩니다.
  끄는 동안 **다른 종목들이 미리 비켜서 자리를 냅니다** — 놓기 전에 어디로 갈지 보이므로 한 번에
  맞출 수 있습니다. 키보드(↑↓)로 옮길 때는 행이 새 자리로 미끄러져 갑니다.
- **히스토리 차트** — 로그 스케일 종가 차트에 **매수(초록, 선 아래) / 매도(빨강, 선 위) 점**만
  찍습니다. 글자는 붙이지 않습니다 — 몇 달치를 한 화면에 놓으면 라벨끼리 겹쳐 선을 가립니다.
  연속으로 뜬 날은 점 하나로 묶습니다.
  점은 **시그널이 뜬 날**에서 나옵니다. 예전에는 매수 실행 기록에서 뽑았는데, 그 기록은 종목을
  등록한 다음 기간부터만 생기기 때문에(스펙: 과거 소급 없음) 매도는 히스토리 전체에 깔리고
  매수는 하나도 없는 일이 흔했고, 차트만 보면 "매도밖에 없는 종목"처럼 보였습니다.
  차트 아래에는 **저장된 시세 구간**이 적힙니다. 고른 기간보다 짧으면 `전체 기간 다시 받기`가
  함께 뜹니다 — 평소 갱신은 최근 2년만 받으므로, 등록할 때 전체를 못 받았으면 그 앞은 다시
  채울 방법이 없었습니다.
- **리밸런싱** — 목표 비중과 현재 비중의 차이를 **금액과 예상 주문 주수**로 환산한 주문 가이드.
  목표 비중은 **현금까지 포함한 전체 자금** 기준이라 현금(원·달러·엔)과 현금 목표를 함께 적습니다.
  "이번에 새로 넣을 돈"을 적으면 그 돈까지 더해 모자란 종목부터 채우는 주문이 나옵니다(저장 안 됨).
  보유수량 옆에 **평단가**를 적으면 평가손익이 보이고, 샀거나 팔았으면 **거래 입력**으로 수량과
  평단가(가중평균)를 고칩니다. 리뷰 주기(분기/반기/연)는 포트폴리오에 하나이고, 리뷰 때 **지금 상태
  기록하기**를 누르면 그날의 모습이 **리밸런싱 기록**으로 남고 다음 리뷰일이 다음 기간으로 넘어갑니다.
- **종목 관리** — **종목명으로 검색해서 추가**(삼성전자 → `005930.KS`). 추가할 때 목표 비중과,
  이미 들고 있으면 수량·평단가를 같이 적습니다. 구분/목표 비중/밴드 설정, 그리고 **비활성화·삭제**. 이름은 검색으로 확정된 값이 들어가되, **국내·일본 종목은
  그 자리에서 고칠 수 있습니다** (일본 종목은 야후가 영문 이름을 주므로 한글로 바꿔 부를 수
  있습니다. 비우면 티커로 돌아갑니다). 시세를 받지 못하면 "등록은 됐지만 시세 실패"를 사유와 함께
  경고로 알려줍니다.

금액·비중을 직접 치는 칸은 **천 단위 콤마**가 붙고(1,000,000), 브라우저가 붙이는 위아래 화살표는
쓰지 않습니다. 붙여넣은 "1,234,567원"에서도 숫자만 걸러냅니다.

종목을 치우는 방법은 두 가지입니다. **목록에서 감추기**(비활성화)는 받아둔 시세·지표·보유수량을
그대로 두고 화면에서만 뺍니다. **완전 삭제**는 그 기록까지 전부 지우며 되돌릴 수 없어, 한 번 더
확인을 받습니다. 둘 다 **대시보드 설정**과 **종목 관리** 어느 쪽에서든 할 수 있고, 확인은 화면
가운데 팝업으로 뜹니다 — 표 아래에 붙이면 종목이 많을 때 화면 밖으로 밀려나 "눌렀는데 아무 일도
안 일어난다"가 됩니다.

헤더의 **전체 새로고침** 버튼으로 활성 종목 전체 시세를 한 번에 갱신할 수 있고, 오른쪽 아이콘으로
다크/라이트 테마를 전환합니다(브라우저에 저장됨).

## 국내·일본주식과 통화

국내주식은 야후 표기(`005930.KS` 코스피 / `247540.KQ` 코스닥)를 쓰지만, **종목 관리 화면에서
종목명이나 6자리 코드로 검색**하면 됩니다.

```
삼성전자   → 005930.KS (코스피)
에코프로비엠 → 247540.KQ (코스닥)
KODEX 200 → 069500.KS (코스피, ETF)
005930    → 005930.KS
```

검색은 이 순서로 찾습니다. 앞에서 찾으면 뒤는 보지 않으므로, 평소 검색은 네트워크 없이 끝납니다.

1. 이미 티커 형태인지 (`VOO`, `005930.KS`)
2. 내장 목록 (`backend/app/data/krx_seed.json` — 주요 종목·ETF, **네트워크가 막혀도 동작**)
3. DB에 캐시된 한국거래소 상장목록
4. 한국거래소 상장목록 온라인 조회 (받으면 캐시)
5. 야후 검색 API

내장 목록은 주요 종목 위주(약 176종목)라 중소형주는 들어 있지 않습니다. 그래서 앱을 켜면
잠시 뒤 백그라운드로 한국거래소 상장목록 전체를 한 번 받아 캐시하고, 이후에는 주 1회
갱신합니다. 못 받아도 내장 목록으로 검색은 계속 됩니다. 종목 관리 화면의 안내 문구가
**지금 무엇으로 검색되고 있는지**(내장 목록인지, 거래소 목록 몇 종목을 언제 받았는지) 그대로
보여줍니다.

> 서버가 임의로 종목을 고르지 않고 **후보를 보여주고 사용자가 확인**하게 돼 있습니다.
> 종목코드를 잘못 짚으면 다른 회사의 시세를 받아오는데, 그건 "못 찾았다"보다 나쁘기 때문입니다.
> 모르는 6자리 코드는 코스피/코스닥을 구분할 수 없으므로 양쪽을 모두 후보로 제시합니다.

### 일본주식

도쿄증권거래소 종목은 야후 표기 `7203.T`(네 자리 코드 + `.T`)를 씁니다. 2024년부터 나온
`130A.T`처럼 **마지막 자리에 영문이 붙는 코드**도 그대로 받습니다.

```
7203.T  → 도요타자동차
6758.T  → 소니그룹
```

이름으로 찾을 때는 위 검색 순서의 **5번(야후 검색)**이 받아줍니다 — 한국거래소 목록에
없는 종목이기 때문입니다. 그래서 일본 종목 검색은 네트워크가 필요하고, 티커를 직접
입력하면 네트워크 없이도 등록됩니다.

**주요 종목 113개는 한글 이름이 내장돼 있습니다** (`backend/app/data/jp_seed.json`).
그래서 아래가 전부 네트워크 없이 찾아집니다.

```
8766      → 8766.T 도쿄해상홀딩스     (증권사 화면에서 보던 네 자리 코드 그대로)
도쿄해상    → 8766.T 도쿄해상홀딩스
toyota    → 7203.T 도요타자동차
유니클로    → 9983.T 패스트리테일링
```

이름은 국내 증권사 표기를 기준으로 적었고, 영문명·다른 표기도 별칭으로 같이 들어 있습니다
(`도쿄마린홀딩스`로 쳐도 찾아집니다).

> **이 목록은 손으로 적은 데이터입니다.** 한국거래소 목록처럼 받아오는 공식 소스가 일본에는
> 없어서, 종목코드가 틀릴 가능성이 0은 아닙니다. **`check-jp.bat`** 을 실행하면 야후가 아는
> 이름을 나란히 찍어주니, 다른 회사로 보이는 줄이 있는지 한 번 훑어볼 수 있습니다.
> 목록에 없는 종목은 티커(`7203.T`)로 등록하면 되고, 이름이 마음에 안 들면 **종목 관리
> 화면에서 그 자리에서 고칠 수 있습니다** — 대시보드·차트·리밸런싱이 모두 그 이름을 씁니다.

시세는 야후를 먼저 쓰고 Stooq로 넘어갑니다(Stooq는 같은 종목을 `7203.jp`로 부르므로
내부에서 바꿔 부릅니다). 네이버는 국내 전용이라 일본 종목에는 쓰지 않습니다.

### 통화

종목의 거래 통화(원/달러/엔)는 티커에서 자동으로 정해지며, 화면 곳곳에서 구분됩니다.

- **가격·주문 금액**은 그 종목을 실제로 거래하는 통화로 표시합니다 (원·엔은 정수, 달러는 센트까지).
- **비중 계산은 반드시 기준통화로 환산한 뒤** 합산합니다. 환산 없이 더하면 달러 1주가 원화 1주와
  같은 무게로 잡혀 비중이 완전히 틀어집니다. 엔은 자릿수가 원과 가까워(1엔 ≈ 9원) 빠뜨려도
  값이 그럴듯해 보이는 만큼 **더 조용히** 틀어집니다.
- 리밸런싱 화면에서 **기준통화(원/달러/엔)를 고르고 적용 환율을 확인·수정**할 수 있습니다.
  환율 칸은 **실제로 들고 있는 통화만** 나옵니다 — 일본 종목이 없으면 엔 칸도 없습니다.
  자동 조회하되 직접 입력한 값이 항상 우선하며, 통화별로 따로 정할 수 있습니다. 조회에
  실패해 추정치를 쓰는 중이면 어느 통화인지와 함께 화면에 표시됩니다.

환율은 **각 통화의 원화 환산값**만 저장하고 나머지는 원을 거쳐 계산합니다. 통화가 셋이면
짝은 여섯이라 짝마다 들고 있을 수 없기 때문입니다 (엔→달러도 원을 거칩니다).

거래일 캘린더도 시장별로 나뉩니다 — 국내는 한국거래소(XKRX), 일본은 JPX, 그 외는 NYSE
휴장일을 따릅니다. 일본은 골든위크·오봉처럼 한국에도 미국에도 없는 연휴가 있습니다.

## 로컬 실행

### Windows — 더블클릭으로 실행

1. **`setup.bat`** — 처음 한 번만 더블클릭 (venv 생성, 패키지 설치, 화면 빌드)
2. **`start-all.bat`** — 그 다음부터는 이것만 더블클릭. **창이 뜨지 않고** 잠시 후 브라우저가 열립니다
3. **`stop.bat`** — 끄기

주소는 **`http://localhost:8000`** 하나입니다. 탭을 닫았거나 나중에 다시 들어가고 싶으면
같은 폴더의 **`신호판 열기`**(`.url` 바로가기)를 더블클릭하면 됩니다 — 서버가 떠 있는
동안은 이것만으로 들어갑니다. (`start-all.bat`을 다시 눌러도 같습니다. 이미 떠 있으면
두 번 띄우지 않고 브라우저만 엽니다.)

**프로세스가 하나입니다.** 예전에는 백엔드와 프런트엔드 개발 서버(vite)가 각자 검은 창에서
떠 있어야 했는데, vite는 *코드를 고칠 때 화면을 바로 바꿔주는 도구*이지 다 만든 화면을
띄우는 데 필요한 게 아닙니다. 화면을 한 번 빌드해두면 백엔드가 그대로 내보냅니다 —
띄울 게 하나, 포트도 하나, 프록시도 CORS도 필요 없습니다.

창이 없어졌으니 **로그는 파일로 남습니다** (`backend/logs/app.log`, 5MB씩 3개 회전).
화면 오른쪽 위 **진단**에서 경고·오류만 골라 보거나 파일째 받을 수 있습니다 — 아래
"문제를 볼 때" 참고.

문제를 눈으로 쫓고 싶으면 **`start-backend.bat`**(창에 로그가 그대로 흐르고 코드 수정 시
자동 재시작). 화면 코드를 고치는 중이라면 **`start-frontend.bat`**으로 vite를 함께 띄웁니다.

- **`update.bat`** — 최신 코드 받기 + 패키지 갱신 + **화면 다시 빌드**를 한 번에 (더블클릭)
- **`diagnose.bat`** — 시세를 못 받을 때 **어디서 막히는지** 진단 (`diagnose.bat TSM`처럼 티커 지정 가능. 국내 티커를 주면 종목명 검색·환율까지 같이 검사합니다)
- **`verify.bat`** — 시세가 들어온 뒤 **받은 값을 믿어도 되는지** 검증 (액면분할 반영, 제공자 간 종가 일치, ETF·우선주·코스닥)
- **`backup.bat`** — 지금 당장 DB를 한 벌 떠둡니다 (평소에는 자동으로 뜹니다 — 아래 "백업" 참고)
- **`check-jp.bat`** — 내장 **일본 종목 목록**의 종목코드가 맞는지 야후와 대조 (`check-jp.bat 8766`처럼 한 종목만도 가능)

> 화면 왼쪽 위에 실행 중인 버전(`v0.9.1 (커밋)`)이 표시됩니다. 업데이트 후에도 값이 그대로면
> 서버를 다시 켜지 않은 것이니, `stop.bat` 뒤에 `start-all.bat`을 다시 실행하세요.

### 백엔드 (수동 실행 / macOS·Linux)

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

`frontend/dist`가 있으면 같은 주소에서 화면도 함께 열립니다 (`cd frontend && npm run build`).
없으면 API만 뜨고, 화면은 아래 개발 서버로 접속하면 됩니다.

최초 실행 시 `signal_dashboard.db` (SQLite)가 자동 생성됩니다. 갱신 스케줄러도 함께 시작됩니다.

| 언제 | 무엇을 |
| --- | --- |
| UTC 22:30 (미국 장 마감 이후) | 활성 종목 전체 |
| UTC 07:00 = JST 16:00 (도쿄 마감 이후) | 일본 종목 |
| UTC 07:30 = KST 16:30 (코스피 마감 이후) | 국내 종목 |
| **앱을 켤 때** | 마지막 거래일보다 뒤처진 시장만 따라잡기 |

마지막 줄이 중요합니다. **정해진 시각에 PC가 꺼져 있으면 그 갱신은 그냥 지나갑니다** — cron은
놓친 실행을 되돌려주지 않습니다. 그러면 시세만 낡는 게 아니라, 그 기간의 매수 시그널 판정도
일어나지 않습니다. 그래서 켤 때 한 번 확인하고, **이미 최신이면 아무것도 하지 않습니다.**

스케줄러 없이 띄우려면 `SIGNAL_DASHBOARD_DISABLE_SCHEDULER=1` 환경변수를 설정하세요.

**DB 위치는 `DATABASE_URL` 하나로 정합니다.** 아무것도 주지 않으면 위의 SQLite 파일입니다.

| | |
| --- | --- |
| `DATABASE_URL=postgresql+psycopg://user:pw@host/db` | 서버 (Postgres) |
| `DATABASE_URL=sqlite:////경로/signal_dashboard.db` | 파일 위치만 옮길 때 |
| `SIGNAL_DASHBOARD_DB=/경로/파일.db` | 예전부터 쓰던 방식. 그대로 동작합니다 |

호스팅이 나눠주는 `postgres://...` 주소도 그대로 붙여넣으면 됩니다 (내부에서 psycopg 드라이버로
바꿔 씁니다).

**스키마 변경은 Alembic이 관리합니다.** 앱이 뜨면서 스스로 최신까지 올리고, 실제로 바꿀 게
있을 때만 **바꾸기 직전에 백업을 한 벌 떠둡니다.** Alembic을 도입하기 전에 쓰던 DB 파일도
그대로 열립니다 — 데이터를 유지한 채 이어받은 뒤 `0001` 리비전으로 표시하고 거기서부터
이어갑니다. 모델을 고치면 리비전을 만들어야 하고, 안 만들면
`tests/test_alembic.py::test_models_and_migrations_do_not_drift`가 잡아냅니다.

```bash
cd backend
alembic revision --autogenerate -m "설명"   # 생성된 내용을 꼭 눈으로 확인하고 커밋
```

### 프런트엔드

```bash
cd frontend
npm install
npm run dev
```

**화면 코드를 고치면서 바로 확인할 때만** 필요합니다. `http://localhost:5173`에서 접속하며,
`/api/*` 요청은 `vite.config.ts`의 프록시 설정을 통해 백엔드(`http://localhost:8000`)로
전달됩니다. 평소 사용에는 필요 없습니다 — 백엔드가 빌드된 화면을 직접 내보냅니다.

## 백업 — 되돌릴 자리

데이터가 사라지면 복구할 방법이 없습니다. 그래서 백업은 켜두는 옵션이 아니라 기본 동작입니다.

| 언제 | 무엇이 |
| --- | --- |
| 앱을 켤 때 | 최근 12시간 안에 뜬 게 없으면 한 벌 (PC는 정해진 시각에 켜져 있다는 보장이 없으므로) |
| 매일 UTC 23:30 | 그날 시세 갱신(22:30)이 끝난 뒤 |
| **스키마를 바꾸기 직전** | 마이그레이션이 잘못 돌면 되돌릴 자리가 여기뿐입니다 |
| `backup.bat` (또는 `python -m app.services.backup`) | 직접 무언가를 크게 바꾸기 전에 |

`backend/backups/`에 최대 7벌 보관하고 오래된 것부터 지웁니다
(`SIGNAL_DASHBOARD_BACKUP_DIR`, `SIGNAL_DASHBOARD_BACKUP_KEEP`로 바꿀 수 있습니다).

**복구는 파일을 제자리에 갖다 놓는 것입니다.** `stop.bat`으로 끈 뒤
`backend/backups/signalboard-….db`를 `backend/signal_dashboard.db`로 덮어쓰면 끝입니다.
압축하지 않는 이유가 이것입니다 — 급할 때 도구를 찾아 헤매야 하는 백업은 없는 것과 비슷합니다.
(Postgres는 `pg_dump` 결과인 `.sql` 텍스트로 뜹니다.)

돌고 있는 파일을 그냥 복사하지 않고 sqlite의 백업 API를 씁니다. 쓰는 중에 복사하면
중간이 찢어진, 열리지 않는 파일이 나올 수 있기 때문입니다.

## 서버에 올리기 — Docker

개인 PC에서는 필요 없습니다. `start-all.bat`이 더 간단하고 SQLite 파일 하나로 충분합니다.
폰에서도 열고 싶거나, PC를 꺼둔 동안에도 갱신되게 하려는 경우입니다.

> **처음 올리는 거라면 [`DEPLOY.md`](DEPLOY.md)를 따라가세요** — 오라클 인스턴스
> 만들기부터 도메인·HTTPS까지 순서대로 적혀 있습니다. 아래는 구성 자체에 대한 설명입니다.

```bash
cp .env.example .env       # POSTGRES_PASSWORD·DASHBOARD_PASSWORD를 직접 채웁니다
docker compose pull        # GitHub이 만들어 올려둔 이미지를 받습니다
docker compose up -d
```

도메인을 붙여 바깥에 공개할 때는 HTTPS를 끊어주는 웹서버를 같이 띄웁니다:

```bash
docker compose --profile https up -d    # .env 에 DOMAIN 이 채워져 있어야 합니다
```

이후 업데이트는 `git pull && docker compose pull && docker compose up -d`. 마이그레이션은
앱이 뜨면서 스스로 돌리고, 그 직전에 백업을 한 벌 떠둡니다.

**서버에서 빌드하지 않습니다.** 무료 티어에서 실제로 잡히는 1GB 인스턴스는 화면
빌드(node) 도중 메모리가 모자라 죽는데, 그게 *이유 없이 멈춘 것*처럼 보입니다. 그래서
GitHub이 푸시마다 이미지를 만들어 GHCR에 올려두고(`ghcr.io/kyos9/dashboard`) 서버는
받기만 합니다. RAM이 넉넉한 곳에서 직접 빌드하려면 `--build`를 붙이면 그대로 됩니다.

- 이미지는 화면(node)과 서버(python)를 각각 빌드해 한 덩어리로 만듭니다. 저장소와 같은
  폴더 구조(`/srv/backend`, `/srv/frontend/dist`)를 유지합니다.
- 남아야 하는 것(로그·백업, SQLite로 쓸 경우 DB)은 전부 `/data` 볼륨 아래입니다.
  이미지 안에 두면 다시 올릴 때 사라집니다.
- 앱 포트는 `127.0.0.1:8000`에만 엽니다. 바깥은 Caddy(`--profile https`)가 맡아
  인증서를 알아서 받고 갱신합니다. 앱을 `0.0.0.0`으로 열면 HTTPS를 건너뛰고 평문으로
  노출됩니다 — 비밀번호가 그대로 오갑니다.
- 워커는 하나입니다. 스케줄러가 앱 안에서 돌기 때문입니다. 실수로 늘리더라도
  **Postgres를 쓰면 스케줄러는 하나만 돕니다** — 어드바이저리 락으로 한 프로세스만
  맡고, 나머지는 조용히 안 띄웁니다(`app/services/leader.py`). 락은 연결이 끊기면
  저절로 풀려서, 앱이 죽어도 다음에 뜨는 쪽이 이어받습니다.

### 비밀번호 하나로 잠그기

`.env`의 `DASHBOARD_PASSWORD`를 채우면 화면과 API 전체가 잠깁니다. **비워두면 잠기지
않습니다** — 개인 PC에서는 그게 맞고(그 주소는 바깥에서 닿지 않습니다), 공개된 주소에
올릴 때는 반드시 채웁니다.

| | |
| --- | --- |
| 여는 방법 | 화면에 뜨는 로그인 칸에 비밀번호를 넣습니다 |
| 유지 기간 | 30일. 서버를 다시 띄우거나 컨테이너를 갈아끼워도 유지됩니다 |
| 안 잠그는 곳 | `GET /api/health` 하나. 컨테이너 헬스체크가 쓰는 자리라 401을 내면 "앱이 죽었다"로 읽힙니다. 대신 잠긴 상태에서는 **상태만** 답하고 버전·제공자는 로그인한 뒤에 알려줍니다 |
| 틀렸을 때 | 5번 틀리면 5분 막습니다 |

- 비밀번호를 **바꾸면 이미 들어와 있던 사람도 전부 나갑니다.** 서명에 비밀번호 지문이
  섞여 있어서, 바꾸는 순간 이미 나간 쪽지가 전부 무효가 됩니다.
- 서명 키는 `/data/session.key`에 남습니다(권한 600). 지우면 모두 로그아웃됩니다.
- **이건 사용자 분리가 아닙니다.** 비밀번호를 아는 사람은 전부 같은 데이터를 봅니다.
  두 번째 사람이 들어오는 시점에 계정으로 바꿉니다 (`ROADMAP.md` 4단계).

### 폰에 설치해서 쓰기

도메인을 붙이고 https로 들어가면, 주소창 없이 앱처럼 열리는 아이콘을 홈 화면에 만들 수
있습니다.

| | |
| --- | --- |
| 안드로이드·PC 크롬 | 헤더의 **앱 설치** 버튼을 누릅니다 (설치할 수 있을 때만 나옵니다) |
| 아이폰·아이패드 | 사파리의 **공유 → 홈 화면에 추가**. 같은 **앱 설치** 버튼을 누르면 그 순서를 보여줍니다 |
| 서버가 안 잡힐 때 | 마지막에 받은 화면이 그대로 뜹니다. 숫자는 비어 있지만 흰 화면이 되지는 않습니다 |

> **https 가 아니면 되지 않습니다.** 브라우저 규칙이라 우회할 방법이 없습니다. 집 안에서
> `http://192.168.0.x:8000` 으로 들어가면 설치 버튼이 뜨지 않고 오프라인 화면도 저장되지
> 않습니다 — 고장이 아닙니다. `localhost` 는 예외라 개인 PC에서는 됩니다.

**시세는 절대 저장하지 않습니다.** 저장하는 것은 화면 껍데기(HTML/JS/CSS)와 아이콘뿐이고,
`/api/` 로 가는 요청은 서비스 워커가 손대지 않습니다. 한 번이라도 저장하면 어제 값이 오늘
값인 척하게 되는데, 그 증상은 *가끔 숫자가 이상하다*로 나타나 원인을 찾기 어렵습니다.
그래서 이 규칙은 테스트가 **실제 배포되는 `sw.js` 를 읽어다 실행해서** 지키는지 봅니다.

새 버전은 화면을 열 때마다 알아서 내려옵니다(껍데기를 항상 네트워크에서 먼저 받습니다).
그래도 옛 화면이 남아 보이면 한 번 더 새로고침하면 됩니다.

아이콘을 고치려면 `frontend/scripts/make_icons.py` 를 고쳐 다시 돌립니다 — 다섯 벌(탭·
안드로이드 2종·마스크용·아이폰)이 한 도형에서 나오므로 따로 그릴 필요가 없습니다.

## 종목 추가 흐름

종목 관리 화면에서 티커를 입력해 추가하면, 백엔드가 전체 히스토리를 백필하고 지표/시그널을
계산합니다. 네트워크가 막혀있거나 실패해도 종목 등록 자체는 유지되며, 이후 "시세 갱신"
버튼으로 재시도할 수 있습니다.

## 시세 수집

한 곳이 막히면 앱 전체가 멈추므로 제공자를 여러 개 두고 순서대로 시도합니다.

| 제공자 | 다루는 시장 | 방식 | 비고 |
| --- | --- | --- | --- |
| `yahoo` | 국내·해외 | yfinance | 봇 차단(쿠키/크럼) 때문에 환경에 따라 막힐 수 있습니다 |
| `stooq` | 해외 | CSV 한 방 | API 키 불필요. 한국거래소는 다루지 않습니다 |
| `naver` | 국내 | 일봉 JSON | API 키 불필요. 야후가 막힌 환경의 국내주식 경로 |

기본 시도 순서는 시장별로 다릅니다.

- 해외: `yahoo` → `stooq`
- 국내: `naver` → `yahoo`

국내주식에 네이버를 먼저 두는 이유는, Stooq가 한국거래소를 다루지 않아 야후가 막히면 국내
종목에는 대체 경로가 아예 없어지기 때문입니다. 다룰 수 없는 티커는 아예 시도하지 않습니다 —
Stooq에 국내 종목을 물어보면 "그런 심볼 없음"이 돌아오는데, 그게 실패 사유로 뜨면 종목코드
오타로 오해하게 됩니다.

모든 제공자의 종가는 분할(split)만 반영하고 배당 재투자 조정은 하지 않은 값이라, 스펙의
investing.com 종가 기준 백테스트와 정합성이 맞습니다.

저장할 때 **어느 제공자가 준 값인지**(`price_daily.source`) 함께 기록하고, 대시보드 카드에
"기준일 2026-09-15 · 네이버 시세"로 보여줍니다. 갱신할 때는 **지금까지 그 종목을 받아온
제공자를 먼저** 시도합니다 — 제공자마다 종가 기준이 조금씩 다를 수 있어서, 한 종목의
히스토리는 되도록 한 곳에서만 받아야 이어붙인 지점에서 지표가 튀지 않습니다. 그쪽이 막혀
있으면 평소 순서대로 넘어가고(값이 없는 것보다는 낫습니다), 출처가 바뀌면 경고 로그가
남습니다. 실제로 두 제공자의 기준이 같은지는 `verify_live.py`가 확인합니다.

### 갱신 속도

전체 새로고침은 종목별로 "조회 → 저장"을 반복하지 않고, **시세를 한꺼번에(동시에) 받아온 뒤
저장만 차례로** 합니다. 조회 시간은 거의 전부 응답을 기다리는 시간이라, 20종목이면 왕복이
20번 쌓이던 것이 동시 4건으로 줄어듭니다 (`MAX_FETCH_WORKERS`). DB 세션은 스레드 간에 나눠
쓸 수 없으므로 저장은 지금처럼 한 줄로 이어서 하고, 한 종목의 실패는 그 종목에만 남습니다.

지표는 갱신할 때마다 과거 전 구간을 다시 계산하지만(중간 값이 조용히 틀어지는 걸 막기
위해서입니다), 저장은 **바뀐 행만** 합니다. 10년치 한 종목 기준 갱신 후처리가 530ms →
105ms로 줄었고, 결과 값은 전과 동일합니다.

환경변수로 조정할 수 있습니다:

- `SIGNAL_DASHBOARD_PROVIDERS` — 공통 시도 순서 (예: `stooq,yahoo`)
- `SIGNAL_DASHBOARD_PROVIDERS_KR` / `SIGNAL_DASHBOARD_PROVIDERS_US` — 시장별 순서 (공통 설정보다 우선)
- `SIGNAL_DASHBOARD_HTTP_TIMEOUT` — 요청 타임아웃 초 (기본 30)

### 문제를 볼 때 — 진단 화면

창이 없어졌으니 로그를 볼 곳이 필요합니다. 화면 오른쪽 위 **진단**을 누르면 서버가 남긴
기록이 뜹니다.

**기본은 경고·오류만** 보여줍니다. 전체 로그를 그대로 쏟으면 대부분이 정상 동작 기록이라
스크롤하다 안 읽게 되는데, 실제로 알고 싶은 건 "어제 VOO 시세를 왜 못 받았나" 한 줄이고
그건 경고 이상만 걸러도 나옵니다(`VOO: [yahoo] CONNECT tunnel failed, 403 Forbidden`).
파이썬 트레이스백은 잘리지 않고 그대로 붙어 나옵니다. 정상 기록까지 보려면 **전체**,
통째로 보내야 하면 **로그 파일 받기**.

| | |
| --- | --- |
| 파일 | `backend/logs/app.log` (5MB × 3 회전) |
| API | `GET /api/logs?level=warning` · `GET /api/logs/download` |
| 안 담는 것 | 접속 기록(`uvicorn.access`) — 요청마다 한 줄씩 쌓여 정작 볼 경고를 밀어냅니다 |

> 로그에는 티커·에러·내부 경로가 찍힙니다. 공개된 주소에 그냥 두면 아무나 봅니다.
> 그래서 서버에서는 `DASHBOARD_PASSWORD`로 **이 화면까지 통째로 잠급니다**
> (위 "비밀번호 하나로 잠그기"). 사용자가 여럿이 되면 남의 기록이 섞이므로 계정 단위로
> 바꿉니다 (`ROADMAP.md` 4단계).

### 시세를 못 받을 때

**`python diagnose.py VOO`** (backend 폴더, 가상환경 활성화 상태)를 실행하면 DNS → 일반
HTTPS → curl_cffi → yfinance → 앱 수집 경로 순으로 나눠 검사해 어느 단계에서 막히는지
알려줍니다. 백신·방화벽의 TLS 간섭인지, 야후의 차단인지, 티커 오타인지 구분됩니다.
국내 티커(`python diagnose.py 005930.KS`)를 주면 시장에 맞는 제공자 순서로 검사하고,
종목명 검색(한국거래소 상장목록)과 환율까지 이어서 확인합니다.

### 받은 값이 맞는지 확인할 때

연결이 되는 것과 값이 맞는 것은 다릅니다. **`python verify_live.py`**는 자동 테스트로
덮을 수 없는 것 — 바깥 서비스가 실제로 무엇을 돌려주는지 — 만 검사합니다:

| 검사 | 틀리면 생기는 일 |
|---|---|
| 네이버 응답의 컬럼 이름 | 컬럼명이 바뀌면 수집이 통째로 멈춤 |
| 액면분할 소급 반영 여부 | 분할일에 가짜 급락이 생겨 그 구간 지표가 전부 틀어짐 |
| 네이버·야후 종가 일치 | 한 시계열에 다른 기준이 섞여 이어붙인 지점에서 지표가 튐 |
| ETF·우선주·코스닥·해외 | 보통주만 되고 나머지가 조용히 실패 |
| 환율 | 통화가 섞인 포트폴리오의 비중이 추정치로 계산됨 |

> 참고: `yf.download()`는 실패해도 예외를 내지 않고 빈 결과를 돌려줘서 원인을 알 수 없습니다.
> 그래서 앱과 진단 스크립트 모두 `Ticker.history(raise_errors=True)`를 씁니다.

## 테스트

```bash
# 백엔드
cd backend && source .venv/bin/activate && pytest

# 프런트엔드
cd frontend && npm test
```

**푸시하면 GitHub이 알아서 돌립니다** (`.github/workflows/`). 커밋 옆에 ✓ / ✗ 가 붙고,
실패하면 메일이 옵니다. PC에는 아무것도 설치되지 않습니다.

| 워크플로 | 언제 | 무엇을 |
| --- | --- | --- |
| `tests.yml` | 푸시할 때마다 | 백엔드 `pytest`를 **SQLite와 Postgres 양쪽**에서 · 프런트 `npm run build`(타입 검사 포함) + `npm test` |
| `docker.yml` | 푸시할 때마다 | 이미지 빌드 → **GHCR에 올리기**(서버가 이걸 받아씁니다) + `docker compose config`·Caddyfile 검사 |

**DB를 둘 다 돌리는 이유.** 내 PC는 SQLite, 서버는 Postgres입니다. SQLite는 타입에
느슨하고 **외래키를 아예 검사하지 않아서** Postgres가 거절할 것을 조용히 받아줍니다.
한쪽만 돌리면 그 차이를 서버에서 처음 만나게 됩니다. 특히 마이그레이션(`0001_initial.py`)이
Postgres에 실제로 적용되는지, 모델이 Postgres가 보는 스키마와 같은지는 여기서만 확인됩니다.

로컬에서 Postgres로 돌려보려면 `TEST_DATABASE_URL`을 주면 됩니다
(`tests/dbsetup.py`가 이 값 하나로 전체 테스트의 DB를 바꿉니다).

```bash
TEST_DATABASE_URL=postgresql+psycopg://postgres:pw@localhost:5432/signal pytest -q
```

Docker 빌드를 매번 돌리지 않는 이유는 무겁기 때문이고(파이썬 패키지 설치 + 화면 빌드),
앱 소스만 바뀌는 경우는 `tests.yml`이 잡습니다. 필요하면 Actions 탭에서 손으로 돌릴 수
있습니다(`workflow_dispatch`).

커버리지를 함께 보려면 `pytest --cov=app` / `npm run test:coverage`.
두 테스트 모두 실제 네트워크를 쓰지 않습니다 — 백엔드는 conftest가 바깥 요청을 막고,
프런트엔드는 API 호출을 가짜로 대체합니다. 네트워크 상태에 따라 결과가 흔들리지
않아야 하고, 시세 서버가 막힌 환경에서도 그대로 돌아가야 하기 때문입니다.

지표(MA/StdDev/ROC/이격도/Wilder DMI-ADX), 시그널 조건식, 매수 워크플로우, 리밸런싱/비중조절
신호, API 라우터까지 단위·통합 테스트로 커버되어 있습니다. yfinance 실제 호출은 네트워크가
필요하므로 테스트에서는 mock 처리됩니다.

`tests/test_knee_conditions.py`는 대시보드가 내려주는 매수 조건 분해가 실제 시그널
엔진(`compute_signals`)과 모든 거래일에서 같은 결론을 내는지 대조합니다 — 두 경로가 갈라지면
화면과 시그널이 어긋나므로 반드시 함께 유지되어야 합니다.

`tests/test_providers.py`와 `tests/test_providers_korea.py`는 응답 파싱·실패 원인 분류·시장별
제공자 라우팅·폴백 동작을 검증하고, `tests/test_data_ingestion.py`는 "야후가 막힌 환경에서
대체 제공자로 받아 지표까지 산출되는지"를 전 구간으로 확인합니다. 실제 네트워크는 쓰지 않습니다.

`tests/test_symbols.py`는 종목명 해석을, `tests/test_fx.py`는 환율 적용 순서를,
`tests/test_rebalance.py`는 통화가 섞였을 때 비중이 기준통화로 환산돼 계산되는지를 확인합니다.
`tests/test_markets.py`는 내장 종목 목록의 형식(6자리 코드·중복 없음)까지 검사하고,
`tests/test_migration.py`는 **기존 DB 파일이 데이터 손실 없이 새 스키마로 올라오는지**를
옛 스키마를 직접 만들어 확인하고, `tests/test_alembic.py`는 그 파일이 다시 만들어지지 않고
*이어받아지는지*와 **모델과 마이그레이션이 벌어지지 않았는지**를 봅니다. 후자가 없으면
모델에 컬럼을 추가하고 리비전을 잊었을 때 내 PC에서는 멀쩡하고 서버에서만 터집니다.
`tests/test_backup.py`는 뜬 백업을 실제로 열어 내용이 들어 있는지까지 확인합니다 —
백업은 뜨는 것보다 복구되는 것이 중요합니다.

프런트엔드(`npm test`)는 계산과 표기를 나눠 검증합니다.

- `src/lib/orderPlan.test.ts` — 주문 계획의 통화 환산. 비중·목표 금액은 기준통화로,
  주문 금액과 주수는 현지 통화로 나오는지 (여기가 틀리면 주문 주수가 환율만큼 어긋납니다)
- `src/lib/display.test.ts` — 통화별 표기(원화 정수 / 달러 센트), 지표 해석, 신호등 판정
- `src/pages/*.test.tsx` — 화면에 실제로 원화·달러가 맞게 찍히는지, 합계가 통화를
  섞어 더하지 않는지
- `src/components/SymbolSearch.test.tsx` — 종목명 검색·후보 선택·키보드 조작
- `src/api/client.test.ts` — 백엔드 오류의 안내(hint)와 기술적 원인(detail) 분리

## 알려진 제약

- 종가는 분할(split)은 반영하되 배당 재투자 조정은 하지 않은 값을 사용합니다 (`SIGNAL_APP_SPEC.md`의
  investing.com 종가 기준 백테스트와 정합성을 맞추기 위함).
- 지원 시장은 한국(코스피/코스닥)과 미국입니다. 다른 거래소를 추가하려면 `app/markets.py`의
  시장 판별과 `app/services/trading_calendar.py`의 캘린더만 늘리면 됩니다.
- 한국거래소 상장목록에는 ETF/ETN이 포함되지 않아, ETF는 내장 목록과 야후 검색으로 찾습니다.
- 시세 출처(`price_daily.source`)는 이 기능이 생긴 뒤 받은 시세부터 기록됩니다. 그 전에 받아둔
  행은 출처가 비어 있습니다 — 다시 내려받게 만들지 않으려고 그대로 뒀습니다.
- **해외주식은 티커로 입력합니다.** 공백 없는 영문 한 단어는 티커로 먼저 해석하므로
  (`VOO`를 네트워크 없이 바로 처리하기 위함), "apple"은 `APPLE`이라는 티커로 잡힙니다.
  회사명으로 찾으려면 "apple inc"처럼 띄어 쓰면 야후 검색까지 진행됩니다.
- 매수 기록은 따로 남기지 않습니다(v0.20.0부터). 대시보드는 종목마다 **매수 시그널이 마지막으로
  뜬 날**을 보여주고, 실제로 샀으면 리밸런싱 화면의 "거래 입력"으로 수량·평단가를 고칩니다.
- 비중조절 신호(밴드 초과/미달, 정기 리뷰 도래)는 참고 알림일 뿐 자동 매매를 트리거하지 않습니다.
  실제로 사고파는 것은 리뷰 때 정합니다.
