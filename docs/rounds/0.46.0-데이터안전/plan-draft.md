## A. 백업 (7 · 8 · 12 · 13)

### A1. 운영 DB 백업을 실제로 되돌려 보는 시험 (7)
- **무엇**: "덤프 → 빈 DB 에 붓기 → 같은지 대조"를 CI 가 매번 한다. 지금 시험의 `pg_dump` 는 늘 가짜다. 되돌리기는 PG16 에서 손으로
  한 번 해 본 것이 전부이고(DEPLOY 10-1), 운영은 PG17 이다.
- **어떻게**
  - 새 시험 `tests/test_backup_restore_pg.py` — Postgres 갈래에서만 돈다. `alembic upgrade head` 로 만든 DB 에 **표마다 실제 같은
    모양의 줄**(사용자 셋·종목·보유·시세·지표·시그널·리밸런싱 기록·평가금액·설정·알림 기기·앱 설정 …)을 넣고,
    **앱의 길 그대로** `backup.create_backup()`(진짜 `pg_dump`) → 새 데이터베이스를 만들어 **DEPLOY 10-1 의 명령 그대로**
    (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;` 뒤 `psql -v ON_ERROR_STOP=1 < 덤프`) 붓는다.
  - 대조: 모든 표의 줄 수, 표마다 기본 키 순으로 줄 내용의 해시, `alembic_version`, 시퀀스(되돌린 뒤 새 줄이 기존 id 와 부딪히지
    않는지 — 새 사용자 하나를 넣어 본다). 되돌린 DB 로 앱의 `init_db()` 가 마이그레이션 없이 뜨는지.
  - 표 목록은 모델(`Base.metadata`)에서 읽는다 — 새 표가 생기면 줄을 안 넣은 표가 있다고 시험이 실패한다(빠짐 막기).
  - **도구가 없거나 판이 안 맞으면 건너뛰지 않고 실패**(CI 에서 `REQUIRE_PG_RESTORE=1`). 로컬 SQLite 갈래에서는 건너뜀.
  - CI(`tests.yml`) Postgres 갈래에 `postgresql-client-17` 설치 단계(PGDG). 러너에 깔린 16 은 17 서버를 덤프하지 못한다.
  - **이미지 쪽**(`docker.yml`): 만든 이미지 안의 `pg_dump --version` 큰 판이 compose 의 `postgres:17` 과 같은지 한 줄로 본다 —
    운영에서 덤프를 뜨는 것은 이미지 안의 `pg_dump` 다(python:3.14-slim 의 데비안 판이 바뀌면 판이 갈라진다).
  - SQLite 갈래: 같은 대조를 `.db` 백업(sqlite3 백업 API)으로 — 이미 있는 시험과 겹치는지 보고 모자란 것만.
- **완료 조건**: CI Postgres 갈래에서 새 시험이 **돌아서** 통과(건너뜀 0). 대조할 표에 빠진 표가 있으면 실패하는 시험. 덤프를 일부러
  깨뜨리면(마지막 줄 자르기) 붓기가 실패로 끝나는 시험. 이미지 판 확인 단계가 docker.yml 에 있음.
- 외부 호출 없음. 화면 바뀜 없음. 되돌리는 법: 시험·CI 단계만이라 커밋 되돌리기.

### A2. `pg_dump` 가 멈추면 기동이 멈춘다 (8)
- **무엇**: `backup.py` 의 `subprocess.run` 에 시간 한도가 없다. 업데이트 직전 필수 백업(`required=True`)에서 걸리면 앱이 뜨지 않은
  채로 기다린다.
- **어떻게**: `timeout=` (기본 600초, `.env` `SIGNAL_DASHBOARD_BACKUP_TIMEOUT` 으로 늘림 — compose 에 넘김). 넘으면 프로세스를 끝내고
  반쯤 쓴 파일을 지우고 실패 갈래 **"pg_dump 가 시간 안에 끝나지 않았습니다"**(진단·⋯ 점에 그대로 뜬다). 필수 백업이면 지금처럼
  업그레이드를 멈추고 DB 는 그대로.
- **기본값**: 600초 — 지금 주인 서버의 덤프는 수 초(DEPLOY 의 예시 8.8MB). 지금보다 나빠지는 경우 없음.
- **완료 조건**: 가짜 `pg_dump`(잠자는 스크립트)로 한도를 넘기면 실패 갈래가 위 문구, 반쯤 쓴 파일이 남지 않음, 필수 백업이면
  `MigrationBackupFailed`. 값이 숫자가 아니거나 0 이하면 기본값.

### A3. 업데이트 직전·켤 때 백업이 7벌을 먹는다 (12)
- **무엇**: 지금 `prune` 은 이름만 보고 최근 7개를 남긴다. 업데이트 직전 백업(`-premigrate`)·손 백업이 같이 세어져, 업데이트가
  잦은 주에는 되돌릴 수 있는 기간이 하루이틀로 준다.
- **어떻게** — 나눠 센다:
  - **매일 백업**(꼬리표 없음): **날짜마다 가장 새것 하나씩, 최근 7일치**(`SIGNAL_DASHBOARD_BACKUP_KEEP` 의 뜻이 "벌"에서
    "날"로 — 이름·기본값 그대로). 같은 날 여러 번 뜬 것(켤 때·손으로)은 그날 안에서 가장 새것만 남는다. **오늘 것은 다 남긴다**
    (방금 손으로 뜬 것이 바로 지워지지 않게 — 10-0-1 의 "지금 한 벌 → 받아 두기").
  - **업데이트 직전 백업**: 따로 최근 3개(`SIGNAL_DASHBOARD_BACKUP_KEEP_PREMIGRATE`, 기본 3).
  - 모르는 꼬리표: 지우지 않는다(사람이 만든 것일 수 있다).
- **기본값이 지금과 같나**: 하루 한 번만 뜨는 서버(보통)에서는 남는 매일 백업이 지금과 같다. 달라지는 것은 업데이트가 있던 주 —
  전에는 지워졌을 매일 백업이 남는다(더 많이 남는 쪽). 디스크: 덤프 하나 수 MB × (7 + 3 + 오늘 몇 개).
- **방침 5절**("서버 백업(하루 한 번, 최근 7벌)에 **최대 7일** 남았다가 차례로 지워집니다", `Policy.tsx:135`): 지금은 모두 7개 안에
  세어지므로 맞다. 업데이트 직전 백업을 따로 세면 업데이트가 뜸할 때 몇 주 남을 수 있다 → **업데이트 직전 백업도 7일이 지나면 지운다**
  (최근 3개 그리고 7일 안). 그러면 "최대 7일"이 그대로 참이다. 방침 문구의 "7벌"은 "7일치"로 고칠지 보고, 고치면 시행일을 바꾼다.
- 진단 응답(`count`·`keep`)은 그대로 두고 `premigrate.keep` 만 더한다(더하기만).
- **완료 조건**: 같은 날 셋 + 지난 8일 하나씩 + 업데이트 직전 다섯 → 남는 것이 정확히 계산대로. 오늘 것은 지우지 않음. 모르는 꼬리표
  그대로. 7일 넘은 업데이트 직전 백업 지움(방침 "최대 7일" 시험). DEPLOY 10 의 "7벌" 설명 고침.

### A4. PC 에 꺼낸 백업이 평문이다 (13)
- **무엇**: `server-backup-pull.bat` 이 받은 `.sql` 에 모든 사람의 보유 기록이 평문으로 있다.
- **생각한 것**: 이 PC 에는 **서버에 들어가는 개인키가 같이 있다**(같은 bat 이 쓴다). PC 를 잃으면 키로 서버의 DB 전체에 닿으므로,
  같은 PC 의 백업만 암호화해서 막는 것은 적다. 반대로 암호를 걸면 **잊으면 백업이 없는 것과 같다**(주인은 개발자가 아니다).
  실제로 막을 만한 길은 (1) 같은 PC 의 다른 윈도 계정이 읽는 것, (2) 폴더가 OneDrive 같은 클라우드로 올라가는 것이다.
- **어떻게(제안)**: bat 이 받는 폴더를 **내 계정만 읽게**(`icacls` 로 상속 끊고 나만) 만들고, 폴더가 OneDrive 아래면 경고하고 멈춘다.
  암호화는 하지 않는다 — DEPLOY 10-0 에 이유 한 단락. → **주인에게 보기로**(아래 "고를 것").
- **완료 조건**: bat 이 폴더 권한을 거는 줄, OneDrive 아래 경로 거절, 문서. (윈도 bat 은 여기서 돌릴 수 없다 — `test_backup_export_script.py`
  처럼 글자로 본다 + 주인 확인 목록.)

## B. 헬스체크가 DB 를 본다 (9)
- **무엇**: `/api/health` 는 DB 가 죽어도 `ok` 다. 컨테이너 헬스체크(Dockerfile)와 가동 확인이 이것을 본다.
- **어떻게**: `SELECT 1` 을 한 번. 되면 지금 응답에 `"db": "ok"` 를 더한다(더하기만). 안 되면 **503** + `{"status": "error", "db": "down",
  "locked": …}` — 오류 글(접속 주소가 들 수 있다)은 응답에 담지 않고 로그에만. 잠긴 상태(로그인 전)에서도 `db` 는 보인다(비밀 아님).
- **영향**: DB 가 죽으면 컨테이너가 `unhealthy` 로 바뀐다. compose 에서 app 의 건강을 기다리는 서비스는 없고(caddy 는 기다리지 않음)
  자동 재시작도 걸리지 않는다 → `docker compose ps` 에서 보이게 될 뿐. 화면 헤더는 503 이면 버전 칸이 비는 것이 지금 코드다(그날은
  어차피 아무 화면도 안 된다).
- **비용**: 헬스체크 30초마다 + 화면을 열 때 한 번. `SELECT 1` 은 커넥션 풀에서.
- **멈춤**: DB 가 응답하지 않고 매달리면 헬스체크 5초 한도에 걸려 `unhealthy` — 의도와 같다. Postgres 접속에 `connect_timeout`
  (5초)을 둔다.
- **완료 조건**: DB 를 끊은(엔진을 망가뜨린) 시험에서 503·`db: down`·오류 글 없음, 평소 200 에 `db: ok`. 옛 필드 그대로(응답 사진 비교).
  `test_isolation` 표 — 주소는 그대로라 바뀜 없음.

## C. 시세 받기 실패를 관리자가 안다 (10)
- **무엇**: 시세 제공자가 막히면(야후 차단 등) 매일 갱신이 조용히 넘어가고 묵은 값으로 화면·알림이 돈다. 지금은 로그에만 남는다.
  0.45 부터 후보로 밀려 있던 것(ROADMAP 0-1 "고도화").
- **어떻게**
  - **기록**: 정해진 시각의 갱신(미국·한국·일본)과 켤 때 따라잡기가 끝날 때마다 시장별로 `{at, total, failed, failed_tickers(최대 10),
    providers(실패한 제공자 이름)}` 와 마지막 성공 시각을 `app_setting` 글자 값 하나(`refresh_status`, JSON)에 적는다. 사람이 누른
    새로고침은 적지 않는다(한 사람의 일이라).
  - **"막혔다"의 기준**: 그 시장에서 받은 종목의 **절반 이상**이 실패(1종목 시장이면 그 하나). 한두 종목 실패(상장폐지 등)는 막힌 것이
    아니다 — 진단에 이름만.
  - **진단(관리자)**: "평가금액 기록 · 백업" 칸 옆에 **"시세 받기"** 한 줄씩 — "미국: 10/30 07:31 받음 · 20종목 중 실패 0",
    막혔으면 "미국: 10/30 07:31 **20종목 중 18개 실패** (yahoo, stooq) — 마지막으로 받은 때 10/28". `/api/admin/records` 에 `refresh` 를
    더한다(더하기만, 관리자 전용 — 실패 종목 이름이 남의 것일 수 있다).
  - **⋯ 점**: 막힌 시장이 있으면 백업처럼 ⋯ 에 점(`backup_attention` 과 나란히 `refresh_attention` 을 더한다).
  - **푸시(관리자)**: 시장이 "막힘"으로 **바뀐 날 한 번**(알림 규칙 1 — 바뀐 순간에만). "시세를 받지 못했습니다 — 미국 20종목 중 18개.
    진단에서 볼 수 있습니다." 다시 받기 시작하면 조용히 풀린다(푸시 없음).
  - **어느 스위치로 끄나**: 새 알림 종류를 만들면 **옛 화면이 넘어진다** — 알림 설정 창이 서버가 준 종류마다 풀이를 찾는데 모르는 종류면
    `undefined.label` 에서 깨진다(`PushModal.tsx:228`). 그래서 새 종류를 만들지 않고 **관리자 전용 "가입 신청" 스위치에 같이 묶는다**.
    서버의 종류 이름(`signup`)은 그대로, 새 화면에서만 이름을 **"관리자 알림 — 가입 신청 · 시세 받기 실패"** 로 바꾼다. 옛 화면에서는
    "가입 신청"으로 보이지만 같이 꺼진다. (다른 길: 서버가 옛 화면엔 새 종류를 숨기는 판 표시 — 더 크다.)
  - `.env` 스위치: `SIGNAL_DASHBOARD_REFRESH_ALERT=off` 이면 푸시만 끈다(기록·진단은 남는다). 서버가 스스로 하는 새 일이라서.
- **바뀌지 않는 것**: 시그널·알림 판단(이미 `SIGNAL_FRESH_DAYS` 로 묵은 시그널은 안 알린다). 사용자 화면.
- **외부 호출**: 늘지 않는다(이미 받은 결과를 적을 뿐).
- **가짜 서버**: 데모에 "일본 막힘"(실패 기록) — 진단 줄·⋯ 점이 보이게. `test_devtools` 에 그 상태.
- **완료 조건**: 절반 기준 경계(10 중 4 → 막힘 아님, 5 → 막힘), 막힘으로 바뀐 날 푸시 한 번·이튿날 또 막혀도 없음·풀렸다 다시 막히면 또
  한 번, 스위치 off 면 푸시 0·기록은 있음, 가입 신청 스위치를 끈 관리자는 푸시 0, 사용자에게는 절대 0, 진단 줄·점, 옛 화면이
  `refresh` 없는 응답(옛 서버)에서 그대로. 응답 사진(사용자 쪽) 변화 0.

## D. 승인 대기·거절·차단 계정 지우기 (11)
- **무엇**: 방침은 "지우고 싶으면 관리자에게 문의"라고 하는데 관리자에게 지우는 수단이 없다(DB 를 손으로 고쳐야 한다).
- **어떻게**: `DELETE /api/admin/users/{id}` — **승인 대기·거절·차단**인 계정만. 쓰는 중(`active`)인 계정은 409 "먼저 차단하세요"
  (실수로 지인의 기록을 지우지 않게 두 단계). 관리자 계정은 403. 없으면 404. 지우는 것은 탈퇴와 **같은 함수**(탈퇴 코드에서 빼낸다) —
  표 목록이 두 곳에서 갈라지지 않게.
- **화면**: 사용자 목록의 그 계정 줄에 **"지우기"** → 확인 창 "○○ 님의 계정과 기록을 지웁니다. 되돌릴 수 없습니다. 같은 구글 계정으로
  다시 가입 신청을 할 수 있게 됩니다." (거절·차단을 지우면 다시 신청을 막던 이유가 사라진다 — 방침 문구와 맞춘다.)
- **방침**: 3절 "거절·차단된 계정의 이메일과 이름은 … 남겨둡니다 … 지우고 싶으면 문의" 뒤에 "관리자가 지우면 같은 계정으로 다시 신청할 수
  있습니다"를 더한다 → `POLICY_EFFECTIVE` 를 바꾼다.
- **격리**: 새 주소를 `test_isolation.py` 표에(관리자 전용 → 사용자 403). 지운 뒤 그 사람의 `user_id` 줄이 모든 표에서 0(탈퇴 검사와 같은 방식).
- **완료 조건**: 셋 상태 지우기 200(또는 204)·active 409·관리자 403·없는 id 404·사용자 403, 지운 뒤 줄 0, 지운 이메일로 다시 신청하면
  승인 대기로 새로 생김, 화면 확인 창, 방침 문구·시행일.
