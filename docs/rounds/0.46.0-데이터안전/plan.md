### A1 복구 시험 (7)
- 원본 DB 와 부을 DB 를 **둘 다 새로 만든다**(AUTOCOMMIT 연결 — 다른 시험이 `signal` 을 비우므로). 원본은 `init_db()` 로 만들고(시드 포함)
  **DB 를 inspect 한 모든 표**(alembic_version 제외)에 실제 같은 줄을 넣는다. 줄을 넣지 않은 표가 있으면 실패(새 표 빠짐 막기).
- 덤프는 앱의 길(`backup.create_backup`, 진짜 pg_dump). **붓기는 운영과 같은 길** — 서비스 컨테이너 안의 psql(`docker exec`)로
  DEPLOY 10-1 명령 그대로(`DROP SCHEMA … CREATE SCHEMA` → `psql -v ON_ERROR_STOP=1`).
- 대조: 표마다 줄 수와 `md5(string_agg(t::text, ',' ORDER BY 기본 키))` 양쪽 비교, `alembic_version`, 시퀀스(새 줄 넣기). **대조가 끝난 뒤**
  되돌린 DB 로 `init_db()` 가 마이그레이션 없이 뜨는지.
- **덤프 끝 확인을 앱에 넣는다**(검토자·개발자 — "마지막 줄 자르기" 시험은 성립하지 않는다): `_backup_postgres` 가 뜬 파일 꼬리에
  `-- PostgreSQL database dump complete` 가 없으면 지우고 실패 갈래 "백업 파일이 끝까지 써지지 않았습니다". 시험: 중간을 자른 덤프 → 거절.
- CI(`tests.yml` Postgres 갈래): PGDG 에서 `postgresql-client-17` 설치 → `echo /usr/lib/postgresql/17/bin >> $GITHUB_PATH` → `pg_dump --version`
  이 17 인지 확인. `REQUIRE_PG_RESTORE=1` 이면 도구·판이 없을 때 건너뛰지 않고 실패.
- 이미지: Dockerfile 에 `ARG PG_MAJOR=17` + `RUN pg_dump --version | grep -q " ${PG_MAJOR}\."` (빌드가 곧 확인). compose 의 `postgres:17` 과 ARG 가
  같은지 파이썬 시험이 글자로 본다. **같은 큰 판**으로 둔다(개발자: 17 덤프는 16 에 부으면 넘어진다 — 붓는 쪽이 같은 판이어야 한다; 검토자의
  "이상"은 덤프만 보면 맞지만 붓기까지 보면 같은 판이 정확하다).
- 덤프 끝 표지는 **꼬리 몇 KB 안에서** 찾는다(17.6 부터 표지 뒤에 `\unrestrict` 줄) — 업데이트 직전 백업에도 걸리므로 CI 의 진짜 pg_dump 17 로 확인(틀리게 거절하면 앱이 안 뜬다).
- DEPLOY 10-1 에 "붓기 전에 `docker compose pull db`"(17.6 부터 덤프에 `\restrict`, 옛 psql 은 멈춘다).

### A2 pg_dump 시간 한도 (8)
- `subprocess.run(timeout=)` 기본 600초. 넘으면 반쯤 쓴 파일을 지우고 갈래 **"백업이 10분 안에 끝나지 않아 멈췄습니다 — 저장된 기록은 그대로입니다. 되풀이되면 서버 로그를 보세요"**(사용자 —
  쉬운 말로, 할 일까지; 분은 설정값에서). 예외 글(접속 주소)은 로그에만.
- `PGCONNECT_TIMEOUT=10` 을 pg_dump 환경에.
- **compose 가 `.env` 를 넘기지 않는다**(개발자 — 지금 `SIGNAL_DASHBOARD_BACKUP_KEEP` 도 서버에서 안 먹는다): `SIGNAL_DASHBOARD_BACKUP_KEEP` ·
  `_KEEP_PREMIGRATE` · `_TIMEOUT` 을 `${…:-}` 로 넘기고, 빈 값·이상한 값이면 기본값(지금 `int()` 는 앱을 죽인다 — 안전 파서로).

### A3 세는 법 (12) — **벌 수로 나눈다**(개발자의 작은 길, 검토자 막음 해소)
- 매일 백업(꼬리표 없음): 최근 **7개**(지금과 같은 뜻). 업데이트 직전 백업: 최근 **3개, 그리고 7일 안**. 모르는 꼬리표는 지우지 않는다.
- 달력으로 세지 않으므로 "8일 실패 뒤 성공 → 한 벌만" 일이 없다(시험 넣음: 8일 실패 뒤 성공해도 매일 백업 7개).
- 방침 "최근 7벌 … 최대 7일": 매일 백업은 지금과 같고 업데이트 직전 백업도 7일을 넘지 않는다 → **방침 문구·시행일 그대로**.
- 백업이 멈춘 동안에는 매일·직전 백업 모두 7일을 넘어 남는다(지금도 같다) — DEPLOY 10 에 한 줄.
- 진단 응답: `keep` 은 "모두 합친 최대"(7+3=10)로 — 옛 화면의 "N개 보관(최대 M개)"가 참으로 남는다. `keep_daily` · `premigrate.keep` 를 더한다.
  새 화면 문구: "매일 백업 N개(최대 7) · 업데이트 직전 N개(최대 3, 7일 안)".

### A4 PC 사본 (13)
- 암호화하지 않는다(추천, 주인 고를 것 2). bat 이 받는 폴더에 `icacls "%DEST%" /inheritance:r /grant:r "%USERNAME%":(OI)(CI)F /T`.
- **못 걸어도(USB·exFAT·네트워크 드라이브) 경고만 하고 받기는 계속**(검토자). OneDrive 아래(`%OneDrive%`·`%OneDriveCommercial%` 접두어)면 **경고만**
  — 멈추지 않는다(검토자·사용자: 매주 받던 것이 조용히 멈춘다).
- 경고는 작업 스케줄러(`/quiet`)에서 창이 안 보인다(사용자 다시 보기) → bat 이 서버에 "꺼냈다"고 적을 때(`backup-export.sh mark`) **경고 표시를 같이 넘기고**,
  진단의 "밖에 꺼낸 것" 줄에 "PC 사본 폴더가 OneDrive 아래에 있습니다(클라우드로 올라갈 수 있습니다)" / "PC 사본 폴더를 나만 열게 하지 못했습니다"가 뜬다.
  옛 서버는 모르는 표시를 무시한다(mark 는 그대로 성공).
- DEPLOY 10-0 에 이유 한 단락. 작업 스케줄러를 다른 계정으로 걸면 그 계정만 열 수 있다 → 주인 확인 목록.

### B 헬스체크 (9)
- `SELECT 1` 은 `get_db` 로(시험이 바꿔 끼운 DB 를 보게). Postgres 면 그 트랜잭션에만 `SET LOCAL statement_timeout = '3s'`(매달린 DB 에서 풀이 마르지 않게).
  엔진 Postgres 갈래에 `connect_args={"connect_timeout": 5}`(모든 접속 — 마이그레이션도 같은 함수).
- 되면 `db: "ok"` 를 더하고, 안 되면 503 `{"status":"error","db":"down","locked":…}`. 오류 글은 로그에만.
- **구글 모드 + 쿠키**(검토자·개발자): 문지기가 먼저 DB 를 봐서 500 이 된다 → `/api/health` 에서만 문지기의 DB 오류(`SQLAlchemyError` 로 좁혀)를 손님으로 넘기고 `request.state.user_id = None` 을 넣어 503 에 닿게. 시험을 두 모드로.

### C 시세 받기 실패 (10)
- **기록**: 정해진 시각 갱신·켤 때 따라잡기 뒤, 결과를 **종목의 시장으로 나눠**(22:30 은 전 시장) 시장마다 키 하나(`refresh_status:US` …)에
  `{at, total, failed, failed_tickers ≤10, providers}` + 마지막 성공. 제공자 이름은 결과 줄에 더한다(`DataIngestionError` 의 원인에서; 오류 글은 담지 않음).
  **받을 종목 0인 실행은 적지 않는다**(검토자 — 막힘→풀림→막힘 두 번째 푸시 막기). `TickerNotFound`(상장폐지)는 세지 않는다.
- **막힘**: (가) 받은 종목의 절반 이상 실패, 또는 (나) **정해진 시각 갱신 뒤에도 그 시장 시세가 마지막 거래일보다 2거래일 넘게 뒤처짐**
  (검토자 — 오류 없이 묵은 값을 주는 제공자. 하루 여유는 제공자가 늦게 올리는 날의 헛울림 막기).
  (나)는 **기록하는 모든 실행**(정해진 시각·켤 때 따라잡기)에 똑같이 적용한다 — 따라잡기가 묵은 값으로 "풀림"을 적고 다음 갱신에 다시 막혀
  푸시가 두 번 가지 않게(검토자 다시 보기). 숫자로: 그 시장 최신 시세 날짜가 마지막 거래일보다 **3거래일 이상** 뒤면 막힘.
- **진단**: "시세 받기" 시장마다 한 줄, 날짜 꼴은 지금 진단과 같게("10월 30일 07:31"), 제공자는 "시세 출처 Yahoo·Stooq". 막혔으면 맨 위 요약
  ("최근 경고·오류 없음")도 그 줄을 따른다(사용자).
- **⋯ 점**: `/api/auth/status` 관리자 갈래에 `refresh_attention`(깨진 값·DB 오류면 점만 포기 — 로그인 응답은 넘어지지 않게). 새 화면의 점 풀이를
  "백업을 확인하세요" → **"진단을 확인하세요"**로 바꾸고 메뉴 안 "진단" 줄에 이유 한 마디(백업/시세). 가입 신청 숫자와는 따로(사용자).
- **푸시**: 막힘으로 **바뀐 날 한 번**. 글: "시세를 받지 못했습니다 — 미국 20종목 중 18개. 진단에서 볼 수 있습니다. (관리자에게만 가는 알림)". 가입 신청처럼 받을 때(아침·오후)를 따르지 않고 바로 간다. 사용자에게는 절대 가지 않는다. 끄는 길은 **이견 1**.
- 새 화면 `KIND_TEXT[kind] ?? 기본 풀이` — 다음부터 새 알림 종류가 옛 화면을 넘어뜨리지 않게(개발자).
- 가짜 서버: 데모에 "일본 막힘". 바뀌지 않는 것: 사용자 화면·시그널·알림 판단. 외부 호출 0.

### D 계정 지우기 (11)
- `DELETE /api/admin/users/{id}` → **204**. 승인 대기·거절·차단만, 쓰는 중 409("먼저 차단하세요"), 관리자 403, 없음 404, 사용자 403(격리 표).
  지우는 것은 탈퇴와 같은 함수 `users.delete_user_records`(탈퇴 코드에서 옮긴다).
- 화면: 줄에 **"지우기"**(맨 끝, 덜 눈에 띄게). 확인 창에 **이름·이메일·종목 수**, 그리고 "거절은 기록을 남겨 다시 신청을 막고, 지우기는 계정과 기록을
  없애 같은 구글 계정으로 다시 신청할 수 있게 합니다. 되돌릴 수 없습니다." 지운 뒤 대기 숫자 다시 세기. ⋯ 위 가입 숫자와 점이 같이 뜨면 숫자가 앞이고 점은 메뉴 안 "진단" 줄에만(겹쳐 그리지 않는다 — 화면 시험).
- 방침 5절(`Policy.tsx:148-149`, 거절·차단 계정 문장 뒤): "관리자가 지우면 같은 계정으로 다시 신청할 수 있습니다. 지운 계정도 서버 백업(최대 7일)과 관리자 PC 사본(최근 4벌)에 남았다가 지워집니다"
  (검토자) → `POLICY_EFFECTIVE` 바꿈. 사용자 목록 위 풀이 "거절·차단해도 기록은 지우지 않습니다" 뒤에 "지우려면 지우기"(사용자).
- 허용목록(`ALLOWED_GOOGLE_EMAILS`)에 있는 이메일은 지운 뒤 다시 오면 바로 쓰는 상태 — 확인 창·DEPLOY 에 한 줄(개발자).

## 이견 — 주인에게

**1. 시세 막힘 알림을 끄는 길** (개발자 ↔ 초안·사용자)

  끄면 시세도 꺼진다"는 헷갈림이 없다. 사용자 걱정(주인이 혼자 못 끈다)은 남는다 — 대신 끌 일이 드물다.
