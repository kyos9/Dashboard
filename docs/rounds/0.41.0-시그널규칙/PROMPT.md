# 키우기 프롬프트 — 자산관리 (v5)

## 주인용 — 붙여 넣지 않는다

**무엇에 쓰나**

* 지금 앱(v0.39.0, 서버에서 실제 사용자와 돌고 있음)을 이어서 키운다.

  * **고도화**: 더 할 수 있게
  * **정교화**: 더 정확하게
  * **전문화**: 더 깊게 보게
  * **사용자화**: 사람마다 맞게
* 한 번 쓰면 **라운드 하나**다. 라운드 하나 = 버전 하나. 다음 라운드에는 같은 글을 다시 쓴다.
* 이 글을 쓰지 않는 경우:

  * 화면 모양만 손볼 때는 `DESIGN_PROMPT.md`를 쓴다.
  * 한두 줄 고칠 작은 요청은 그냥 말로 하면 된다.

**도는 모양 — 라운드는 이렇게 이어진다**

* 라운드 → 배포(주인) → 며칠 써 보기 → 불편한 점·새 요청 → 다음 라운드.
* AI가 하는 사용자 확인은 가짜 데이터로 걷는 것이라, **주인이 실제로 써 본 느낌을 대신하지 못한다.** 다음 라운드의 "쓰면서 불편한 점" 칸이 그 느낌을 받는 자리다.
* 다음 라운드 후보는 매 라운드 끝에 `ROADMAP.md` 0-1 "다음 라운드 후보"에 쌓인다. 무엇을 할지 막막하면 거기서 고른다.
* 한 번에 라운드 하나만 연다. 디자인 작업(`DESIGN_PROMPT.md`)과 동시에 돌리면 같은 파일(`index.css`·화면 코드)을 고쳐 부딪힌다.

**쓰는 법**

1. 아래 ✂ 부분의 **"주인이 채울 칸"**을 채운다. 하고 싶은 게 막연하면 "방향"만 고르고 "구체 요청"은 비워 둔다. 그러면 총괄이 후보를 골라 온다.

   * 거슬리는 화면은 스크린샷을 같이 준다. 이때는 대시보드의 **금액 가리기**를 켜고 찍는다.
2. ✂ 표시부터 끝까지 복사해, 이 저장소를 연 Claude Code 새 세션에 붙여 넣는다.
3. 라운드 도중 세션이 끊기면 새 세션에서 **"이어서 해 줘"** 한 줄이면 된다.

   * 라운드를 시작할 때 이 글이 `docs/rounds/`에 저장된다.
   * 저장소 맨 위 `CLAUDE.md`(세션이 열릴 때 저절로 읽힘)가 그 자리를 가리킨다.

**주인에게 묻는 때**

* 정해진 때는 세 번이다. 막혔을 때만 그 사이에 묻는다.

  * ① 계획 승인 — 이번 라운드에 할 것, 크기, 규제·데이터 영향.
중간·큰 라운드면 개발자·검토자·사용자 세 입장이 초안을 한 번씩 검토한 **최종 계획**과, 의견이 갈린 곳(**이견**)이 보기로 같이 온다
  * ② 큰 라운드면 중간 확인 — 첫 항목을 마친 뒤
  * ③ 끝 보고 — **배포 안내**와 주인 확인 목록 포함
* 질문은 늘 **보기 2~4개 + 추천 + 스크린샷**으로 온다.
* 채팅에 붙여 넣으면 안 되는 것: `.env` 값, 비밀번호, 개인키, DART·AI 키.

# ✂ 여기부터 끝까지 붙여 넣는다

당신은 이 저장소의 **자산관리** 앱을 이어서 키우는 라운드의 **총괄**이다. 이 글 전체가 작업 지시다.
**지금 코드와 문서가 설계도다.** 새로 짓지 않고, 이미 정한 것을 지키면서 더한다.

**맨 처음 할 일**
0. **다른 브랜치에서 진행 중인 작업 확인** — 같은 저장소를 다른 세션이 동시에 고치고 있을 수 있다(예: 디자인 작업).

* `git fetch origin` 뒤 기본 브랜치(`git remote show origin`의 HEAD)를 확인하고, 다른 원격 브랜치마다 기본 브랜치에 아직 없는 커밋이 있는지 본다(`git log origin/<기본>..origin/<브랜치>`).
* 있으면 브랜치마다 적는다: 마지막 커밋 날짜·메시지, 고친 파일(`git diff --stat origin/<기본>...origin/<브랜치>`), 진행 표시(`docs/design/`, `docs/rounds/*/status.md`의 상태).
* **이번 라운드와 겹칠 수 있으면 시작 전에 주인에게 묻는다.** 겹치는 것: 같은 파일(특히 `frontend/src/index.css`·화면 코드), 새 Alembic 리비전(같은 번호를 두 브랜치가 만들면 합칠 때 머리가 둘이 된다), 같은 문서 절. 보기:

  * 그 작업을 먼저 끝내고 합친 뒤 시작 (추천)
  * 겹치지 않는 항목만 이번에 (예: 서버 쪽만)
  * 그대로 진행 — 합칠 때 충돌을 각오
* 기본 브랜치에 이미 다 들어간 브랜치, 한 달 넘게 손대지 않은 브랜치는 `status.md`에 목록으로만 남긴다.
* 남의 브랜치는 읽기만 한다. 고치거나 합치거나 지우지 않는다.
* 라운드 도중에도 커밋·푸시 전에 한 번씩 `git fetch`로 다시 보고, 새로 생긴 겹침은 `status.md`에 적어 끝 보고에 올린다.
1. `docs/rounds/`에 진행 중(`status.md`의 상태가 "진행 중")인 라운드가 있으면, 새로 시작하지 말고 그 라운드를 잇는다.

   * 주인이 새 요청을 붙여 넣었는데 진행 중인 라운드가 있으면, 둘 중 무엇을 할지 먼저 묻는다(이어서 끝내기 / 새 요청을 그 라운드에 더하기 / 새 요청은 다음 라운드로).
2. 없으면 새 라운드 폴더 `docs/rounds/<다음 버전>-<한두 단어>/`를 만든다. 그 안에 둔다:

   * `PROMPT.md` — 이 글 전체, 주인의 답 포함
   * `status.md`
3. 저장소 맨 위 `CLAUDE.md`에 아래 줄이 없으면 더한다(파일이 없으면 만들고, 디자인 작업이 만든 줄이 있으면 그대로 둔다). 둘 다 커밋·푸시한다.

```
진행 중인 라운드가 있으면 docs/rounds/ 에서 status.md 의 상태가 "진행 중"인 폴더를 찾아,
그 폴더의 PROMPT.md 와 status.md 를 먼저 읽고 status.md 에 적힌 자리부터 잇는다.
```

## 지켜야 할 선 — 이 라운드에서도 바뀌지 않는다

**규제** (`ROADMAP.md` 3절). 이 앱이 투자자문으로 읽히지 않게 하는 선이다. 문구가 아니라 실질로 판단된다.

* 하지 않는 것:

  * 유료화
  * 종목 추천, 종목끼리 순위를 매겨 고르게 하기
  * 자동 매매
  * 수익률 광고
  * AI의 매수·매도 권유·가격 예측·"저평가" 판단
  * 화면의 "추천"이라는 말
  * 매크로 합성 점수, 사라·팔아라로 읽히는 색
* **이 선에 닿는 항목은 기획 때 "규제 영향"으로 따로 적고 주인이 정한다.** 예: 백테스트 수익률을 화면에 보여 주기, 종목 비교 순위.

**데이터 경계** (`ROADMAP.md` 1절)

* 새 테이블·컬럼마다 두 가지를 먼저 정한다.

  * 공용인가 사용자별인가
  * **다시 만들 수 있는가**
* 다시 만들 수 없는 것은 **지금 기록을 시작하지 않으면 영영 없다.** 기획 때 맨 위에 올린다.

  * 예: 거래 내역, 날마다의 포트폴리오 가치. 지금은 보유가 덮어쓰기라 과거 수익률을 복원할 수 없다.
* 지표(`indicator_daily`)는 공용이다. 사람마다 다른 판단은 **임계값을 사용자 설정으로 두고 읽을 때 계산**한다(싼 개인화).
* 지표 기간을 사람마다 바꾸는 것(비싼 개인화)은 정해 둔 몇 가지를 미리 계산해 둘 때만 한다. 자유 입력은 받지 않는다.

**사용자와 권한**

* 요청에는 언제나 사용자가 있다.
* 남의 자원은 404, 주인 전용은 403으로 답한다.
* 새 엔드포인트는 `test_isolation.py` 표에 적어야 테스트가 통과한다.

**AI**

* 키는 기기 브라우저에만 둔다. 서버는 중계만 하고 저장·기록하지 않는다.
* 보내는 데이터 범위는 지금 그대로다.

  * 정리: 공용 숫자만
  * 진단·분석: %만
* 범위를 넓히려면 다음을 같이 고치고 주인이 정한다:

  * "보내는 내용 보기"
  * 개인정보처리방침
  * 규제 영향

**시그널 정의 — 주인이 쓰면서 바꿀 수 있다**

* 무릎매수·어깨매도의 조건·임계값·조건 개수는 **주인이 정하면 바뀐다.** 이 글의 "바뀌지 않는 선"이 아니다. 다만 바꾸는 방법은 정해져 있다.
* 바꾸면 **과거 판정이 같이 바뀐다**(저장된 시세로 다시 계산한다). 차트의 지난 점, "마지막 매수 시그널" 날짜가 달라진다. 그게 대개 원하는 동작이지만 주인에게 전후를 보여 주고 정한다.
* **지금 규칙은 여러 곳에 따로 적혀 있다** — 하나만 고치면 화면·AI·알림이 서로 다른 기준을 말한다. 바꿀 때 다 같이 고친다(또는 먼저 한 곳으로 모은다 — §1 후보 "시그널 규칙을 한 곳으로"):

  * `SIGNAL_APP_SPEC.md` 3·4장(정의) — **먼저 고친다**(명세 10장 순서)
  * `backend/app/services/signals.py` — `compute_signals`와 `knee_conditions` **두 군데**에 같은 임계값이 있다
  * `frontend/src/lib/display.ts` — 조건 이름표·열 머리글·풀이(`ADX > 20`, `> 1.1` 등)와 색 판정
  * `frontend/src/pages/Dashboard.tsx` — 시그널 보기 설명 문장

  * `README.md` "화면 구성"
* **바꾼 뒤 보이는 것**:

  * 전후 비교를 주인에게 보인다: 종목별 지난 1·3·5년 발동 횟수, 오늘 상태가 바뀐 종목, 마지막 매수 시그널 날짜가 바뀐 종목. (수익률로 보여 주지 않는다 — 규제)
  * 알림: 오늘 상태가 바뀐 종목은 배포 뒤 첫 판정에서 알림이 갈 수 있다. 몇 명·몇 종목인지 세어 끝 보고에 적는다. 지난 날짜의 변화로는 알림이 가지 않는지 확인한다.

  * API 필드 이름(`knee_buy_v2`, `shoulder_sell_ref`)은 바꾸지 않는다 — 옛 화면이 쓴다. 뜻은 명세가 정하고, 명세에 "정의 변경 이력"(날짜·무엇·이유)을 남긴다.

## 운영 중인 앱이라 생기는 규칙

서버에는 남의 실제 데이터가 있고, 폰에는 옛 화면이 캐시돼 있다.

* **기본값은 지금과 같게**

  * 새 설정·새 기능은 켜기 전까지 지금과 **같은 결과**를 낸다.
  * 사용자화 항목의 기본값은 지금 값이다(예: ADX 기준 20).
* **마이그레이션**

  * 지금 리비전에 **실제와 같은 모양의 데이터**를 넣고 올려 보는 테스트를 SQLite·Postgres 둘 다에서 돌린다.
  * 되돌릴 수 없으면:

    * 백업 성공을 조건으로 건다.
    * `DEPLOY.md`에 업데이트 주의를 적는다.
    * 끝 보고에 크게 적는다.
* **옛 화면 ↔ 새 서버, 새 화면 ↔ 옛 서버**

  * 응답 필드는 **더하기만** 한다. 빼거나 뜻을 바꾸지 않는다. 시작 때 떠 둔 API 모양과 끝의 것을 비교해, 빠진 경로·필드가 0인지 본다.
  * 화면은 서버가 새 필드를 안 보내도 깨지지 않게 한다(지금도 "옛 서버는 닫힘으로 본다"). 옛 모양의 응답을 넣는 화면 테스트로 확인한다.
  * 요청에 새 필드를 더하면 서버는 그 필드가 없어도 받는다(옛 화면이 보낸다).
* **새 입력의 한도**: 사용자가 보내는 새 값(설정·문자열·목록)은 크기·범위를 서버가 검사한다. 사람 수만큼 곱해지는 새 외부 호출에는 한도를 건다(기존 한도는 `services/limits.py`).
* **이름**: 이미 띄운 서버의 설정·쿠키·저장 키 이름은 바꾸지 않는다.
* **배포는 주인이 한다.** 끝 보고에 순서·주의·되돌리는 법을 적는다.
* **가짜 서버**

  * 새 바깥 접점이나 새 화면 상태(새 설정, 새 오류)가 생기면 `devtools` 데모 데이터에도 넣는다.
  * `tests/test_devtools.py`가 통과해야 한다.
* **방침**: 수집하는 것이 늘면 개인정보처리방침·이용약관을 같이 고친다.

## 운영 방식 — 누가 어느 역할을 맡나

|역할|누가|이유|
|-|-|-|
|기획자 · 실행자|총괄|주인과 이야기하고, 맥락을 이어 구현한다|
|계획 검토 — 개발자·검토자·사용자|**새 서브 에이전트 셋**, 동시에, 읽기만|계획 단계에서 잡으면 문장만 고치면 된다. 개발 뒤에 잡으면 코드·테스트·검토를 다시 돈다|
|검토자|**새 서브 에이전트**, 자기 git worktree|만든 사람의 생각을 모르는 눈. 뮤테이션은 파일을 고치므로 작업 트리를 나눈다|
|사용자|**새 서브 에이전트**, 전용 포트|코드를 모르고 화면만 보는 눈|

* **언제 부르나**

  * 계획 검토: 라운드 크기 "중간·큼", 또는 마이그레이션·규제 영향이 있는 라운드. "작음"이고 둘 다 없으면 건너뛴다(§1 5단계).
  * 개발 뒤 검토자·사용자: 크기 "중간·큼" 항목은 항목마다, "작음" 항목들은 묶어서 한 번. 라운드 끝에 전체 회귀·호환을 보는 검토를 한 번 더 한다.
* **검토자에게 넘기는 것**:

  * 항목의 완료 조건
  * 커밋 범위와 **라운드 시작 커밋**, 시작 때 떠 둔 기준 두 가지의 경로
  * 규제 영향 항목에 대한 주인의 결정(`status.md`)
  * 이 글의 "지켜야 할 선"·"운영 중인 앱이라 생기는 규칙"·§3
  * 앞 판정의 "조건부" 목록
  * 계획 검토 의견서 셋(`plan-*.md`) — 계획 때 나온 걱정이 풀렸는지부터 본다
* **검토자가 지키는 것**:

  * 고치지 않는다. 커밋하지 않는다.
  * 끝날 때 자기 worktree의 `git status`가 깨끗한지 확인한다.
* **사용자에게 넘기는 것**:

  * 가짜 서버를 띄우는 명령과 전용 포트
  * 이번 과업(§4)
  * 스크린샷 둘 곳(저장소 밖)
* **사용자가 지키는 것**:

  * 코드를 읽지 않는다.
  * 띄운 서버는 **PID로** 끈다.
* **판정문**: 둘의 판정문은 총괄이 손대지 않고 라운드 폴더에 커밋한다(`<항목>-review.md`, `<항목>-user.md`).
* **불합격이면**:

  * 총괄이 고친다.
  * **새** 검토자를 부르고, 이전 판정문을 넘긴다.
  * 같은 항목이 세 번 불합격이면 주인에게 묻는다.
* **`status.md`**: 항목 시작·판정·주인 질문 때마다 고치고 **커밋·푸시**한다.

  * 적는 것: 상태(진행 중/끝), 항목과 체크, 마지막 판정, 남은 조건부, 주인 질문과 답, 다음 할 일.
* `.claude/agents/`에 검토자·사용자 정의가 없으면 첫 라운드에서 만든다. 다음 세션부터는 이름으로 부른다.

  * 계획 검토의 검토자·사용자 입장은 같은 정의에 "이번엔 계획 검토 — 읽기만, §1 6단계 형식으로"를 붙여 부른다. 개발자 입장은 일반 에이전트로 부른다.
  * 계획 검토의 사용자 입장도 화면을 띄우면 개발 뒤 사용자와 같은 규칙(전용 포트, PID로 끄기)을 따른다.

**실행 환경에서 못 하는 것** — 우회하지 않고 대신할 길:

* 바깥 인터넷

  * 가짜 서버로 확인한다.
  * 실제 출처는 주인이 `diagnose.bat`·`verify.bat`로 본다.
* Docker: CI가 확인한다.
* 아이폰 사파리·실기기 알림: 주인 확인 목록으로 넘긴다.
* 갤럭시 크롬: Playwright 폰 360px로 대신 본다.
* 조직 정책 거부(403·407): 재시도·우회하지 않고 보고한다.

## 1. 기획자 (총괄)

**할 일: 이번 라운드에 무엇을 할지 정하고, 주인 승인 ①을 받는다.**

1. **지금 상태 확인** — §0을 읽고 실제와 다른 점을 적는다. 시작 수치와 기준 두 가지를 뜬다. `ROADMAP.md` 0-1에서 **주인이 할 일로 남은 것**(배포·규제 확인 등)을 옮겨 둔다 — 이번 라운드에 걸리는 것이 있으면 계획에 적는다.
2. **요청 정리** — 주인 요청마다 네 방향 중 어디인지 적는다. 요청이 비었으면 `ROADMAP.md` 0-1 "다음 라운드 후보"와 아래 후보 목록에서 3~5개를 고른다. 주인이 쓰는 모습(9단계 요청들)에 가까운 것부터. **이미 한 것은 빼고**(ROADMAP·README에서 확인), 주인 요청이 모호하면 주인 말을 바꿔 쓰지 말고 해석 두세 가지를 보기로 묻는다(9-13 에서 "맨 끝"을 잘못 읽은 일이 있었다).
3. **항목마다 적는 것**:

   * 무엇(주인 말로 한 줄)
   * 왜
   * 크기(작음·중간·큼)
   * 규제 영향(없음 / 있음 → 무엇)
   * 데이터

     * 새 테이블·컬럼인가
     * 공용인가 사용자별인가
     * **다시 만들 수 있나**
     * 마이그레이션이 되돌릴 수 있나
   * 외부 호출이 느는가(사람 수만큼 곱해지는가)
   * 부딪히는 기존 결정(ROADMAP의 절 번호)
   * 되돌리는 법(스위치·기본값)
4. **순서** — 주인 요청이 먼저다. 다만 기록을 시작해야 하는 것(다시 못 만드는 것)이 관련되면 "지금 시작하지 않으면 그 전 기록은 영영 없다"를 맨 위에 적어 주인이 정하게 한다.
5. **크기 맞추기** — 라운드 크기를 넘으면 나눠서 다음 라운드 후보로 남긴다.
6. **계획 검토 — 세 입장이 한 번씩** ("언제 부르나"에 해당할 때만)

   * 위 1~5로 쓴 초안을 라운드 폴더 `plan-draft.md`로 저장·커밋하고, 서브 에이전트 셋을 **동시에** 부른다. 셋 다 읽기만 하고 고치지 않는다.

|입장|보는 것|읽을 것|
|-|-|-|
|개발자|정말 만들 수 있나 · 크기가 맞나 · 마이그레이션·호환 · 지금 코드와 부딪히는 곳(파일:줄) · 더 작은 길|초안 + 관련 코드·테스트|
|검토자|규제 영향 · 데이터 경계(공용/사용자별, 다시 만들 수 있나) · 보안·입력 한도 · 외부 호출 · 되돌릴 수 있나 · 확인 방법이 있나|초안 + "지켜야 할 선"·"운영 중인 앱이라 생기는 규칙" + 관련 코드|
|사용자|주인 요청을 제대로 읽었나(원문과 대조) · 정말 필요한가 · 설명 없이 찾을 수 있나 · 말이 쉬운가 · 매일 쓰는 흐름을 방해하나|초안 + 주인 원문 + 가짜 서버 화면(지금 화면, 코드는 읽지 않음)|

* **형식은 하나**: 항목마다 `찬성 / 걱정 / 제안`, 걱정마다 심각도(막음·고쳐야 함·참고)와 근거. 한 사람에 한 쪽 안. 파일은 `plan-dev.md`·`plan-review.md`·`plan-user.md` — 총괄이 손대지 않고 커밋한다.
* **한 번만 돈다.** 반박·재반박을 하지 않는다. 총괄은 걱정마다 `반영 / 반영 안 함(이유) / 주인에게`로 답을 적어 최종 계획 `plan.md`를 만든다.
* **다시 묻는 건 딱 하나의 경우**: 반영하면서 항목을 바꾸거나 새로 넣었으면, 그 **바뀐 부분만** 그 걱정을 낸 입장에게 한 번 더 보인다. 그 외에는 다시 돌지 않는다.
* **"막음" 걱정을 "반영 안 함"으로 넘기지 않는다** — 고치거나, 주인에게 올린다.
* 셋의 의견이 갈리면 총괄이 대신 정하지 않는다. **이견** 칸에 양쪽 이유를 그대로 두고 주인에게 보기로 올린다.
7. **주인에게** — 최종 계획(항목 표) + **이견**(보기 2~4개 + 추천) + 반영 안 한 걱정과 그 이유 + 고를 것. 규제 영향이 있는 항목은 따로 묶어 보인다. 계획 검토를 건너뛰었으면 그렇다고 적는다.

**정교화 — 더 정확하게**

* **시그널 규칙을 한 곳으로** — 시그널 로직을 바꾸기 전에 먼저 하면 좋다.

  * 지금 임계값과 조건 문구가 6곳 넘게 흩어져 있다(위 "시그널 정의"의 목록). 서버의 한 곳(규칙 정의)에서 계산·화면 이름표·AI 지시문이 모두 가져오게 한다(화면은 API로 받는다 — 옛 서버면 지금 문구로).
  * 그러면 로직을 바꿀 때 한 곳 + 명세 + 테스트만 고치면 되고, 사용자화(개인 임계값)도 같은 정의 위에 얹힌다.
  * 화면이 보이는 결과는 그대로여야 한다(회귀 검사의 응답 사진과 같음).
* **시그널 임계값의 근거 복원**

  * 명세에 "백테스트 결과·임계값 근거 복원 못 함"이 적혀 있다.
  * 저장된 시세로 시그널의 발동 빈도와 그 뒤 N일의 움직임 분포를 재는 **내부 검증 보고서**를 만든다(문서·주인 전용).
  * 화면에 수익률로 보이면 규제 영향이 있다.
* **데이터 품질 자동 점검**

  * 제공자 간 종가 대조, 분할 누락·급변 탐지, 재무 공시 시점 검증.
  * 지금 `verify.bat`가 손으로 하는 것을 매일 돌리고, 이상이 있으면 진단 화면에 띄운다.
* **주문 가이드 정밀도**: 주수 반올림 방향, 최소 거래 단위, 쓰는 환율의 시점 표시.
* 오류·경계 문구 정리: 사용자가 실제로 본 오류를 진단 로그에서 찾아 문장 다듬기.

**전문화 — 더 깊게 보게**

* **기록 시작이 먼저**: 거래 내역(샀다·팔았다 입력을 덮어쓰지 않고 남기기), 날마다의 포트폴리오 가치. 이것 없이는 아래 성과 지표가 불가능하다.
* **위험 지표** — 지금 데이터로 바로 된다:

  * 포트폴리오 변동성
  * 최대 낙폭
  * 종목 간 상관
  * 실질 종목 수
  * 통화·시장 노출
* **성과**: 기간 수익률, 현금 흐름을 뺀 시간가중 수익률(기록 시작 뒤부터). 남과 비교하거나 광고하지 않는다.
* 리밸런싱 시뮬레이션: "목표를 이렇게 바꾸면 주문이 어떻게 되나"를 저장 없이 미리 보기.
* 세금·수수료 반영 — 명세 8장에서 범위 밖으로 둔 것. 주인 결정.

**사용자화 — 사람마다 맞게**

* **시그널 임계값 개인 설정**

  * 대상: ADX 기준(20), 거래량비(1.1), 이격도 기준(0), 비교 기간(5거래일).
  * 사용자 설정으로 두고 읽을 때 계산한다. 공용 표는 그대로다(ROADMAP 1절 "싼 개인화").
  * 화면에는 "내 기준" 표시와 "기본값으로" 버튼을 둔다.
  * 알림·차트 점도 내 기준을 따를지 정한다.
* 첫 화면 탭 고르기, 대시보드 칸 고르기·순서.
* 알림 종류·시간 개인 설정(고도화의 알림과 함께).
* AI 요청 서식 저장(지금은 종류마다 하나 기억) — 여러 개 저장하고 고르기.

## 2. 실행자 (총괄)

**항목마다**:

1. `status.md`에 그 항목의 작업 목록을 적는다.
2. 서버 → 화면 → 가짜 서버 데모 → 문서 순으로 만든다. 커밋은 작게 나누고, 푸시마다 CI를 확인한다.
3. 확인한다:

   * 단위 테스트
   * 경계값
   * **뮤테이션** — 핵심 줄 10개 안팎을 되돌려 테스트가 잡는지 본다. 결과는 파일로.
   * 마이그레이션 두 DB
   * 격리 표
   * 브라우저 — PC 1400 · 폰 390/360 × 다크·라이트. 가로 넘침·잘린 글자·44px·대비·콘솔 오류.
4. 검토자·사용자를 부른다(운영 방식).

**라운드 끝에**:

* **버전**: `backend/app/version.py`에 한 줄 설명을 단다. 기능이 늘면 0.x.0, 고치기·다듬기만이면 0.x.y.
* **ROADMAP**:

  * 단계 기록을 남긴다(9단계처럼 표 + 절). 키우기 라운드는 **11장 "키우기 라운드"** 아래에 `11-N`으로 이어 적는다(10장은 디자인 다듬기다. 11장이 없으면 만든다). 한 것, 계획과 달라진 것, 정한 것과 이유.
  * 0-1 "지금 남은 것"과 **"다음 라운드 후보"**를 고친다(이번에 나눠 미룬 것 + 하면서 보인 것, 네 방향으로).
* **`status.md`**: 상태를 "끝"으로 바꾸고 커밋·푸시한다. 그래야 다음 라운드가 이 라운드를 이어 붙잡지 않는다.
* **README**: "화면 구성"에 버전별 항목을 더한다.
* **바꿨다면 같이 고칠 것**: 명세(시그널), `DEPLOY.md`(배포), 방침(수집 항목).
* **시작 수치와 비교**: 테스트 수가 줄지 않고, lint 경고가 늘지 않는다.
* 전체 테스트 출력은 저장소 밖 파일로 두고, 보고에 경로를 적는다.

## 3. 검토자 (항목마다 새 서브 에이전트)

실행자의 보고를 믿지 않고 직접 돌린다. 해당 없는 칸은 "해당 없음"이라고 적는다.

|검사|방법|합격|
|-|-|-|
|완료 조건|기획 표의 그 항목|전부|

## 4. 사용자 (항목마다 새 서브 에이전트)

코드를 읽지 않고, 가짜 서버 화면으로만 써 본다.

|사람|데모 계정|보는 것|
|-|-|-|
|주인 (PC·아이폰, 매일)|`owner@example.com`|새 기능이 매일 보는 흐름을 방해하지 않는지|
|지인 (갤럭시만, 주식 초보)|`friend@example.com`|새 기능을 설명 없이 찾고 이해하는지. 새 용어에 풀이가 있는지|
|처음 온 사람|`new@example.com`|종목 0개에서 새 기능이 어떻게 보이는지|
|승인 대기 · 손님|`pending@example.com` · 로그인 안 함|새 기능이 새어 보이지 않는지|

**과업**

* **이번 과업**: 기획자가 항목마다 1~3개를 정한다. 사용자의 말로 쓴다. 예: "내 ADX 기준을 25로 바꾸고, 오늘 매수 시그널이 몇 개로 바뀌는지 본다".
* **회귀 과업**: 매번 걷는다.

  1. 오늘 매수 시그널이 뜬 종목을 찾아 차트에서 그 날을 확인한다
  2. 새로 넣을 돈 100만 원으로 주문 가이드를 받는다
  3. 여러 종목의 수량·평단가를 한 번에 고친다
  4. 금액을 가리고 손익 %만 본다
  5. 폰 뒤로가기로 팝업을 닫는다
* **사용자화 항목이 있으면 더 걷는다**: 설정을 바꿨다가 **기본값으로 되돌리기** — 되돌리는 길을 설명 없이 찾는지, 되돌린 뒤 화면이 처음과 같은지. 바꾼 설정이 어디에 쓰이고 있는지(내 기준인지 기본인지) 화면에서 알 수 있는지.

**그 밖의 조건**

* 상승 색 빨강
* 확대 150%(창 933px, 배율 1.5)
* 아주 긴 종목명
* 억 단위 금액

**결과**

* "막힌 곳 / 헷갈린 말 / 찾지 못한 것 / 좋았던 것" 표로 낸다.
* 줄마다 사람·과업·스크린샷 경로·심각도(못 끝냄 / 헤맴 / 거슬림)를 적는다.
* 고칠 방법은 적지 않는다.

## 5. 합격 기준

* 모든 항목이 검토 합격이고 조건부가 비어 있다. CI 두 갈래가 초록이다.
* 시작 수치보다 테스트 수가 줄지 않고, lint 경고가 늘지 않는다.
* 새 기능을 켜지 않으면 이전 버전과 같은 결과가 나온다.
* 옛 화면·새 서버, 새 화면·옛 서버 어느 쪽도 깨지지 않는다.
* 이번 과업과 회귀 과업에 "못 끝냄"이 없다.
* 문서(README·ROADMAP·version.py, 바뀌었다면 명세·DEPLOY·방침)가 코드와 맞는다.
* `status.md`가 "끝"이고 푸시돼 있다.
