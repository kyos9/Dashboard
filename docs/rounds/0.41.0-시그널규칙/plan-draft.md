## 1. 지금 실제 모습 (§0 과 대조)

- 스택·리비전(0012)·테스트 두 갈래는 §0 과 같다. 코드 버전 0.40.0 = 서버 0.40.0.
- 시그널 정의가 적힌 곳 — §0 목록과 같고, 더 찾은 것:
  - `display.ts` `trafficLight` 의 "매수 조건 **4개**를 모두 만족" 문장
  - `schemas.KneeConditions` / `types.ts KneeConditions` — **조건 네 개가 필드 이름으로 박혀 있다.** 조건 수가 바뀌면 API 모양을 바꿔야 한다
  - 화면은 조건을 **지표 칸**(이격도·ADX·DI·거래량) 에 하나씩 붙인다(`CONDITION_BY_METRIC`). 다른 지표에 걸린 조건이 생기면 붙일 칸이 없다
  - `ai_analysis.py` 조건 줄(`① -DI>+DI … ④ ADX>20`)과 "네 조건 중 n개" 문장, `ai_portfolio.py` 가 `SIGNAL_RULES` 를 같이 씀
- 지난 판정의 재계산: 매일 갱신(`refresh_ticker`)이 그 종목의 **전체 기간** 시그널을 다시 계산해 덮는다(`recompute_signals`).
  그래서 정의를 바꿔 배포하면 **다음 갱신 때** 종목마다 따라 바뀐다. 그 사이(배포 ~ 다음 갱신)는 화면의 오늘 조건(읽을 때 계산 — 새 정의)과
  저장된 `signal_daily`(옛 정의)가 **서로 다른 말을 한다.** 보는 사람이 없는 종목(갱신 대상 아님)은 계속 옛 정의로 남는다.
- 알림(`alerts.py`)은 종목마다 **가장 최근 행**의 `knee_buy_v2` 만 본다 → 지난 날짜의 판정이 바뀌어도 알림은 안 간다(확인 필요 — B 에서 테스트로 박는다).
- 리밸런싱 기록(`RebalanceSnapshot`)은 그날 값을 저장해 둔다 → 재계산 대상이 아니다.

## 2. 항목

### A. 시그널 규칙을 한 곳으로 — 정교화 · **중간~큼**

**무엇**: 무릎매수·어깨매도의 조건·임계값·문구를 서버 한 파일(`services/signal_rules.py`)에 **데이터로** 적고, 계산·화면·AI 가 모두 거기서 가져온다.
**정의는 바꾸지 않는다** — 화면·응답·AI 지시문이 지금과 똑같아야 한다.

**왜**: 지금은 임계값 하나(ADX 20)를 바꾸려면 8곳 이상을 같이 고쳐야 하고, 하나라도 빠지면 화면·AI·알림이 서로 다른 기준을 말한다.

만드는 것:
1. `signal_rules.py` — 규칙 하나 = 조건 목록. 조건마다: 키, 붙는 지표 칸(`metric`), 비교(지표·연산자·임계값 또는 "N거래일 전 값"), OR 묶음,
   화면 이름표·풀이·열 머리 문구, AI 문구. 임계값 상수(ADX 20, 거래량비 1.1, 이격도 0, 비교 5거래일)는 여기 한 번만.
   정의 판(`version`, 예: `"knee-v2"`)과 **변경 이력**(날짜·무엇·이유)도 여기.
2. `compute_signals`(표 전체, 벡터 계산)와 `knee_conditions`(오늘 한 줄)가 **같은 조건 정의를 평가**한다. 두 군데 임계값을 없앤다.
   두 길이 같은 답을 내는지 무작위 시세로 비교하는 테스트(오늘 한 줄의 판정 == 표 전체 계산의 마지막 행).
3. AI 지시문(`SIGNAL_RULES`, 조건 줄, "네 조건 중 n개")을 정의에서 만든다. **지금 문장과 글자 하나까지 같은지** 테스트로 박는다.
4. API (**더하기만**)
   - `GET /api/signal-rules` — 공용·읽기만. 매수·매도 규칙의 조건 목록·문구·정의 판·이력. 격리 표에 `(SHARED, GUEST)` 로 적는다(로그인 전 화면도 시그널 설명을 보므로 — 확인 필요).
   - 대시보드 카드에 `buy_conditions: {키: true|false|null}` (규칙의 키 그대로, 조건 수가 바뀌어도 모양이 그대로). 옛 `knee_conditions` 네 칸은 그대로 채운다.
5. 화면
   - 규칙을 API 로 한 번 받아 쓴다(앱 상태에 보관, 탭을 옮겨도 다시 안 받음). **옛 서버**(404)면 지금 문구(`display.ts` 의 지금 표)로 — 그 표는 "옛 서버용 기본값"으로 남는다.
   - 열 머리·조건 표시·시그널 보기 설명 문장(`Dashboard.tsx:879`)·신호등 풀이("조건 4개")를 규칙에서.
   - 붙일 지표 칸이 없는 조건(앞으로 생길 수 있음)은 시그널 설명 줄과 폰 펼친 곳에 "그 밖의 조건"으로 보인다 — 이번엔 데모로만 확인.
6. 명세: 3·4장에 "정의는 `signal_rules.py` 가 갖고 이 장은 그 뜻을 적는다", 10장 바꾸는 순서를 새 길로, **11장 정의 변경 이력** 신설.

- 규제 영향: **없음** (문구·정의 그대로, 새 판단 없음)
- 데이터: 새 테이블·컬럼 없음. 마이그레이션 없음
- 외부 호출: 늘지 않음. `/api/signal-rules` 는 정적 내용
- 부딪히는 기존 결정: 없음. 필드 이름 `knee_buy_v2`·`shoulder_sell_ref`·`knee_conditions` 유지(§0 "그대로 두는 것")
- 되돌리기: 커밋 되돌리기. 화면은 서버가 규칙을 안 주면 지금 문구로 돈다
- 완료 조건: 시작 때의 응답 사진과 같음(새 필드 제외) · AI 지시문 글자 같음 · 임계값 숫자가 `signal_rules.py` 밖(테스트·명세 제외)에 없음 —
  `grep` 로 검사하는 테스트 · 옛 응답(새 필드·새 엔드포인트 없음)으로 화면 테스트 통과

### B. 정의를 바꿀 때의 길 — 자동 재계산 + 전후 비교 — 정교화 · **중간**

**무엇**: 정의를 고쳐 배포하면 (1) 서버가 알아서 **모든 종목의 지난 판정을 저장된 시세로 다시 계산**하고, (2) 바꾸기 전에 주인이
"무엇이 달라지나"를 숫자로 볼 수 있게 한다.

**왜**: §1 에서 본 "배포 ~ 다음 갱신 사이 두 기준이 섞이는" 틈과, 명세 10장·이 프롬프트가 요구하는 **전후 비교**(발동 횟수·오늘 상태·마지막 매수 시그널 날짜)를 사람이 손으로 하지 않게.

만드는 것:
1. **정의 지문** — `signal_rules.py` 정의에서 만든 해시. 앱이 뜰 때(스케줄러를 맡은 프로세스 하나만, `leader.py`) 저장된 지문(`app_setting` 한 줄,
   `signal_rules_fingerprint`)과 다르면 **뒤에서** 전 종목 `recompute_signals` → 지문 저장. 네트워크 없음.
   - 0.41.0 첫 배포: 저장된 지문이 없으므로 한 번 돈다 — 정의가 같아서 바뀌는 행 0 (이걸 확인 항목으로)
   - 걸리는 시간: ROADMAP 9-1 기준 종목 하나 10년치 0.25초 → 서버 종목 수 × 0.25초. 도는 동안 화면은 옛 판정을 보인다(지금과 같은 모습)
   - 기록: 바뀐 행 수(종목별)와 시각을 로그 + 진단 화면(주인만)에 한 줄
2. **전후 비교 도구** — `python -m app.tools.signal_diff` (주인·개발용, 화면 없음). 저장된 `signal_daily`(지금 서버의 판정)와 코드의 정의로 다시 계산한 것을 비교:
   종목별 지난 1·3·5년 발동 횟수(전→후), 오늘 상태가 바뀐 종목, 마지막 매수 시그널 날짜가 바뀐 종목, **오늘 상태가 새로 켜져 알림이 갈 사람 수·종목 수**.
   수익률·그 뒤 움직임은 **넣지 않는다**(규제). 쓰는 때: 정의를 고친 코드를 띄우기 전(주인 PC, 백업 DB 로) 또는 개발 세션(가짜 서버 DB 로).
3. 알림: 재계산이 지난 날짜만 바꾸면 알림 0, 오늘이 새로 켜지면 다음 알림 판정에서 한 번 — 테스트로 박는다.
4. 가짜 서버: 데모에 "정의를 바꿨다"는 상태를 만들 수 있게(지문을 일부러 옛 것으로) — 재계산이 돌고 진단에 한 줄 뜨는 것을 화면으로 확인.

- 규제 영향: **없음** — 비교 도구는 발동 횟수만, 주인 전용, 화면 없음
- 데이터: `app_setting` 에 줄 둘(지문, 마지막 재계산 요약) — 공용, **다시 만들 수 있음**(없으면 한 번 다시 계산). 새 테이블·마이그레이션 없음
- 외부 호출: 없음 (저장된 시세만)
- 부딪히는 기존 결정: 없음 (`app_setting` 은 9-15 에서 "쓰다가 바뀔 수 있는 앱 전체 값"으로 만든 표 — 성격이 맞는지 검토 의견 받기)
- 되돌리기: 정의를 되돌린 코드를 배포하면 지문이 다시 달라져 옛 판정으로 다시 계산된다(같은 길)
- 완료 조건: 지문이 다르면 한 번만 돈다(두 번째 시작에는 안 돈다) · 워커 둘이면 하나만 · 재계산 중 실패해도 앱이 뜬다 · 비교 도구가 가짜 서버 DB 에서
  정의를 일부러 바꾼 경우 기대한 숫자를 낸다 · 알림 테스트
