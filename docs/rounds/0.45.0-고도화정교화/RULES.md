# 키우기 라운드 규칙 (v6)

`EVOLVE_PROMPT.md` 의 붙여 넣는 글이 이 파일을 가리킨다. 이 글 전체가 총괄의 작업 지시다.

당신은 이 저장소의 **자산관리** 앱을 이어서 키우는 라운드의 **총괄**이다.
**지금 코드와 문서가 설계도다.** 새로 짓지 않고, 이미 정한 것을 지키면서 더한다.

- 라운드 하나 = 버전 하나. 주인이 붙여 넣은 칸(방향·요청·불편한 점…)이 이번 라운드의 입력이다.
- **이 파일은 라운드를 시작할 때 라운드 폴더에 `RULES.md` 로 복사한다.** 라운드 도중에는 그 복사본을 따른다 —
  이 파일이 라운드 사이에 고쳐져도 진행 중인 라운드의 규칙은 바뀌지 않는다.

## 맨 처음 할 일

0. **다른 브랜치에서 진행 중인 작업 확인** — 같은 저장소를 다른 세션이 동시에 고치고 있을 수 있다(예: 디자인 작업).
   - `git fetch origin` 뒤 기본 브랜치(`git remote show origin`의 HEAD, 지금은 `main`)를 확인하고, 다른 원격 브랜치마다
     기본 브랜치에 아직 없는 커밋이 있는지 본다(`git log origin/<기본>..origin/<브랜치>`).
   - 있으면 브랜치마다 적는다: 마지막 커밋 날짜·메시지, 고친 파일(`git diff --stat origin/<기본>...origin/<브랜치>`),
     진행 표시(`docs/design/*/status.md`, `docs/rounds/*/status.md`의 상태).
   - **이번 라운드와 겹칠 수 있으면 시작 전에 주인에게 묻는다.** 겹치는 것: 같은 파일(특히 `frontend/src/index.css`·화면 코드),
     새 Alembic 리비전(같은 번호를 두 브랜치가 만들면 합칠 때 머리가 둘이 된다), 같은 문서 절. 보기:
     - 그 작업을 먼저 끝내고 합친 뒤 시작 (추천)
     - 겹치지 않는 항목만 이번에 (예: 서버 쪽만)
     - 그대로 진행 — 합칠 때 충돌을 각오
   - 기본 브랜치에 이미 다 들어간 브랜치, 한 달 넘게 손대지 않은 브랜치는 `status.md`에 목록으로만 남긴다.
   - 남의 브랜치는 읽기만 한다. 고치거나 합치거나 지우지 않는다.
   - 라운드 도중에도 커밋·푸시 전에 한 번씩 `git fetch`로 다시 보고, 새로 생긴 겹침은 `status.md`에 적어 끝 보고에 올린다.
1. **작업 브랜치 맞추기**
   - 세션에 정해진 브랜치가 있으면 그것, 없으면 `claude/` 아래 새 브랜치. 기본 브랜치에 직접 푸시하지 않는다.
   - 그 브랜치의 지난 PR이 **이미 합쳐졌으면** 기본 브랜치 끝에서 다시 시작한다(같은 이름으로).
     합쳐진 PR에 새 커밋을 쌓지 않는다.
2. `docs/rounds/`에 진행 중(`status.md`의 상태가 "진행 중")인 라운드가 있으면, 새로 시작하지 말고 그 라운드를 잇는다.
   - 주인이 새 요청을 붙여 넣었는데 진행 중인 라운드가 있으면, 둘 중 무엇을 할지 먼저 묻는다
     (이어서 끝내기 / 새 요청을 그 라운드에 더하기 / 새 요청은 다음 라운드로).
3. 없으면 새 라운드 폴더 `docs/rounds/<다음 버전>-<한두 단어>/`를 만든다. 그 안에 둔다:
   - `PROMPT.md` — 주인이 붙여 넣은 글 그대로(채운 칸 포함)
   - `RULES.md` — 이 파일의 복사본
   - `status.md`
4. 저장소 맨 위 `CLAUDE.md`에 아래 줄이 있는지 본다(없으면 더하고, 디자인 작업이 만든 줄은 그대로 둔다). 커밋·푸시한다.

```
진행 중인 라운드가 있으면 docs/rounds/ 에서 status.md 의 상태가 "진행 중"인 폴더를 찾아,
그 폴더의 PROMPT.md 와 status.md 를 먼저 읽고(RULES.md 가 있으면 그것도) status.md 에 적힌 자리부터 잇는다.
```

**주인 칸이 비었을 때**

| 칸 | 비우면 |
| --- | --- |
| 방향 | 고도화 · 정교화 · 전문화 · 사용자화 중 총괄이 후보를 골라 온다 |
| 구체 요청 | `ROADMAP.md` 0-1 "다음 라운드 후보"(+ §1 씨앗 목록)에서 3~5개를 제안한다 |
| 절대 바꾸지 말 것 | 아래 "지켜야 할 선" + `ROADMAP.md`에 정한 것 |
| 라운드 크기 | 중간 (항목 2~4개). 작게 = 1개, 크게 = 5개 이상 또는 마이그레이션 둘 이상 → 나누기를 권한다 |
| 서버에 올라가 있는 버전 | 계획 승인 때 진단 화면 왼쪽 위 버전을 한 줄로 묻는다. 그때까지는 서버가 **이 라운드 시작 시점의 코드보다 옛것**이라고 가정한다 |
| 주로 쓰는 기기 | 아이폰(사파리·홈 화면 앱) + 갤럭시(삼성 인터넷·크롬) + PC 크롬 |

**주인에게 묻는 때**
- 정해진 때는 세 번이다. 막혔을 때만 그 사이에 묻는다.
  - ① 계획 승인 — 할 것, 크기, 규제·데이터 영향. 중간·큰 라운드면 세 입장이 검토한 **최종 계획**과 **이견**이 보기로 같이 간다.
  - ② 큰 라운드면 중간 확인 — 첫 항목을 마친 뒤
  - ③ 끝 보고 — **PR 링크·배포 안내**와 주인 확인 목록 포함
- 질문은 늘 **보기 2~4개 + 추천 + 스크린샷**으로 한다. 주인은 개발자가 아니다 — 명령·용어 대신 결과로 묻는다.
- 주인에게 받지 않는 것(채팅에 붙여 넣게 하지 않는다): `.env` 값, 비밀번호, 개인키, DART·AI 키.

**지금 상태는 이 글에 적지 않는다 — 직접 재서 `status.md` 첫머리에 적는다.** (이 글에 숫자를 적어 두면 라운드마다 낡는다.)
- 버전: `backend/app/version.py`의 `APP_VERSION`
- Alembic 머리: `cd backend && alembic heads` (또는 `migrations/versions/`의 마지막 번호)
- 스택·실행·CI: README·`DEPLOY.md`·`.github/workflows/`. 다음은 바뀌지 않았다고 가정하지 말고 한 번 본다:
  FastAPI + SQLAlchemy + Alembic / React + Vite + TS / PC는 SQLite, 서버는 Postgres / Docker(GHCR) + Caddy /
  CI는 SQLite·Postgres 두 갈래 테스트 + Docker 이미지(기본 브랜치에서만 `latest`를 올린다 — **서버가 받아쓰는 태그**).
- 사용자·권한: 구글 로그인, 가입 신청 → 주인 승인. 권한은 주인과 사용자 둘(`is_owner`). AI는 주인 스위치로 연다.

**라운드를 시작할 때 재서 `status.md`에 적는 것.** 끝에 이보다 나빠지면 안 된다.
- 시작 커밋(이 라운드의 비교 기준)
- 백엔드 테스트 수(`pytest -q`), 프런트 테스트 수(`npm test`)
- lint 경고 수(`npm run lint`), `npx tsc -b` 통과
- 대시보드 응답 시간·쿼리 수(20종목)
- 첫 화면 JS 크기(`npm run build` 출력의 gzip 크기)

**같은 날 같이 떠 두는 기준 두 가지** — 저장소 밖(스크래치 폴더)에 둔다. 끝의 회귀·호환 검사가 이것과 비교한다.
- **API 모양**: `python -c "import json; from app.main import app; print(json.dumps(app.openapi()))"`의 출력.
- **응답 사진**: 가짜 서버(`--reset`, 데이터가 정해져 있다)를 띄우고 주인·친구 계정으로 받은 응답.
  - 대상: `/api/dashboard`, `/api/rebalance/current`, `/api/fundamentals`, `/api/macro`, `/api/history/NVDA`
  - 가짜 시세는 오늘 날짜까지 만들어지므로 **비교는 같은 날 하거나, 날짜·시각 필드를 빼고** 한다.

### 가짜 서버 다루기 — 모든 역할이 같은 방법으로

- **먼저 화면을 빌드한다.** 가짜 서버는 `frontend/dist`(빌드한 화면)를 내준다. 화면을 고친 뒤
  `cd frontend && npm run build`를 하지 않으면 **옛 화면**을 보고 판정하게 된다.
- **띄우기** — 셸을 붙잡지 않게 떼어 띄우고 PID를 적어 둔다:
  ```
  cd backend
  (nohup python -m devtools.fake_server --port <포트> --data-dir <저장소 밖 폴더> --reset > <로그> 2>&1 < /dev/null & echo $! > <pid 파일>)
  ```
  `$(...)`로 감싸 띄우면 셸이 끝나지 않는다.
- **끄기** — 적어 둔 PID로만: `kill $(cat <pid 파일>)`. **`pkill -f`·`killall`은 쓰지 않는다** —
  명령줄에 같은 글자가 든 자기 셸·남의 서버까지 죽인다.
- **포트를 나눈다** — 총괄 8150, 계획 검토의 사용자 8160, 개발 뒤 사용자 8170부터 항목마다 하나씩 올린다.
  데이터 폴더도 역할마다 따로 둔다.

## 지켜야 할 선 — 이 라운드에서도 바뀌지 않는다

**규제** (`ROADMAP.md` 3절). 이 앱이 투자자문으로 읽히지 않게 하는 선이다. 문구가 아니라 실질로 판단된다.
- 하지 않는 것:
  - 유료화
  - 종목 추천, 종목끼리 순위를 매겨 고르게 하기
  - 자동 매매
  - 수익률 광고
  - AI의 매수·매도 권유·가격 예측·"저평가" 판단
  - 화면의 "추천"이라는 말
  - 매크로 합성 점수, 사라·팔아라로 읽히는 색
- **이 선에 닿는 항목은 기획 때 "규제 영향"으로 따로 적고 주인이 정한다.** 예: 백테스트 수익률을 화면에 보여 주기, 종목 비교 순위.

**데이터 경계** (`ROADMAP.md` 1절)
- 새 테이블·컬럼마다 두 가지를 먼저 정한다.
  - 공용인가 사용자별인가
  - **다시 만들 수 있는가**
- 다시 만들 수 없는 것은 **지금 기록을 시작하지 않으면 영영 없다.** 기획 때 맨 위에 올린다.
  - 예: 거래 내역(아직 없다). 날마다의 평가금액은 0.44.0에서 기록을 시작했다(`portfolio_value_daily`).
- 사용자별 새 표는 탈퇴 때 지워지는지 `test_isolation.py`의 탈퇴 검사가 본다(`user_id` 칸이 있는 모든 표).
- 지표(`indicator_daily`)는 공용이다. 사람마다 다른 판단은 **임계값을 사용자 설정으로 두고 읽을 때 계산**한다(싼 개인화 —
  0.42.0 "내 기준"이 이 방식이다).
- 지표 기간을 사람마다 바꾸는 것(비싼 개인화)은 정해 둔 몇 가지를 미리 계산해 둘 때만 한다. 자유 입력은 받지 않는다.

**사용자와 권한**
- 요청에는 언제나 사용자가 있다.
- 남의 자원은 404, 주인 전용은 403으로 답한다.
- 새 엔드포인트는 `test_isolation.py` 표에 적어야 테스트가 통과한다.

**AI**
- 키는 기기 브라우저에만 둔다. 서버는 중계만 하고 저장·기록하지 않는다.
- 보내는 데이터 범위는 지금 그대로다.
  - 정리: 공용 숫자만
  - 진단·분석: %만
- 범위를 넓히려면 다음을 같이 고치고 주인이 정한다: "보내는 내용 보기", 개인정보처리방침, 규제 영향.

**시그널 정의 — 주인이 쓰면서 바꿀 수 있다**
- 무릎매수·어깨매도의 조건·임계값·조건 개수는 **주인이 정하면 바뀐다.** "바뀌지 않는 선"이 아니다. 다만 바꾸는 방법은 정해져 있다.
- 바꾸면 **과거 판정이 같이 바뀐다**(저장된 시세로 다시 계산한다). 차트의 지난 점, "마지막 매수 시그널" 날짜가 달라진다.
  그게 대개 원하는 동작이지만 주인에게 전후를 보여 주고 정한다.
- **정의는 `signal_rules.py` 한 곳에 있다**(0.41.0). 계산·화면 문구(`GET /api/signal-rules`)·AI 지시문이 모두 여기서 가져온다.
  바꾸는 순서(명세 10장):
  1. `SIGNAL_APP_SPEC.md` 3·4장(정의) — **먼저 고친다**
  2. `signal_rules.py` — 기준값·조건·`CHANGES`. 평가 동작을 바꿨으면 `VERSION`을 손으로 올린다(지문이 바뀌어야 서버가 지난 판정을 다시 계산한다)
  3. 테스트 — `test_signal_rules.py`·`test_signals.py`·`test_knee_conditions.py`·`test_spec.py`의 경계값
  4. `backend/devtools/fake_server.py` — 데모 데이터가 일부러 시그널을 만드는 모양(`dip`·`rally`). 새 정의에서도 뜨는지 `test_devtools.py`로 확인
  5. 화면의 옛 서버용 규칙(`frontend/src/lib/signalRulesLegacy.json`) — `/api/signal-rules`가 없는 옛 서버면 화면이 이걸 쓴다.
     지금은 서버 기본 응답과 글자까지 같아야 한다(서버 테스트가 본다). 정의를 바꾸면 이 둘이 갈라진다 — 그 테스트를 어떻게 바꿀지 계획에 적는다
  6. `README.md` "화면 구성", `DEPLOY.md` 9-1
  - 다 고친 뒤 `grep`으로 옛 기준값(예: `20`, `1.1`)이 `signal_rules.py` 밖에 남았는지 본다.
- **바꾼 뒤 보이는 것** — `python -m app.tools.signal_diff`(DB에 쓰지 않는다)로 잰다:
  - 종목별 지난 1·3·5년 발동 횟수(전→후), 오늘 상태가 바뀐 종목, 마지막 매수 시그널 날짜가 바뀐 종목. **수익률로 보여 주지 않는다**(규제).
  - 배포 뒤 첫 판정에서 알림이 새로 갈 사람·종목 수. 끝 보고에 적는다. 지난 날짜의 변화로는 알림이 가지 않는지 확인한다.
  - 화면 어딘가에 "시그널 기준을 바꾼 날"을 한 줄 남길지 주인에게 묻는다.
- **그대로 두는 것**:
  - API 필드 이름(`knee_buy_v2`, `shoulder_sell_ref`, `knee_conditions`의 키)은 바꾸지 않는다 — 옛 화면이 쓴다. 뜻은 명세가 정하고, 이력은 `CHANGES`와 명세 11장에 남긴다.
  - 리밸런싱 기록·날마다의 평가금액은 다시 계산하지 않는다(그날의 사실이다).
  - 사용자별 임계값("내 기준")은 공용 `signal_daily`를 바꾸지 않는다. 공용 정의를 바꾸는 것과 사람마다 다르게 보는 것은 다른 일이다 — 계획에서 어느 쪽인지 분명히 한다.
- 정의 변경은 **라운드 하나에 하나**만, 다른 큰 항목과 섞지 않는다. 문제가 생기면 그 커밋만 되돌릴 수 있게.

**디자인**: 새 화면도 `DESIGN_PROMPT.md` §0 규칙을 따른다.

**개발과 디자인의 경계** — 주인 요청이 화면에 닿을 때:
- **뜻·동작·문구가 바뀌면 이 라운드가 맡는다.** 예: 신호를 두 줄로 나누기, 관망을 숨기기, "매도 검토"를 "비중 초과"로.
  이때 `docs/design/glossary.md`와 README "화면 구성"을 같이 고친다.
- **색·간격·배치·글꼴만 바뀌면 디자인 작업(`DESIGN_PROMPT.md`)으로 넘긴다.** 계획에 "디자인 후보"로 적고
  `ROADMAP.md` 0-1에 남긴다. 주인이 이번에 하자고 하면 그때 넣는다.

**이미 정한 것**: `ROADMAP.md`에 이유와 함께 적힌 결정은 다시 묻지 않는다.
- 예: 매수 예정·확정 흐름을 걷어낸 것, 금액 가리기의 범위, 내부 이름 `SIGNAL_DASHBOARD_*`를 그대로 둔 것.
- 이번 라운드가 그것과 부딪히면 **"뒤집기"**로 따로 적고, 원래 이유와 함께 주인에게 보인다.

## 운영 중인 앱이라 생기는 규칙

서버에는 남의 실제 데이터가 있고, 폰에는 옛 화면이 캐시돼 있다.

- **기본값은 지금과 같게**
  - 새 설정·새 기능은 켜기 전까지 지금과 **같은 결과**를 낸다.
  - 사용자화 항목의 기본값은 지금 값이다(예: ADX 기준 20).
  - 서버가 스스로 하는 새 일(예: 매일 기록)에는 끄는 스위치(`.env`의 `SIGNAL_DASHBOARD_*`)를 둔다.
- **마이그레이션**
  - 지금 리비전에 **실제와 같은 모양의 데이터**를 넣고 올려 보는 테스트를 SQLite·Postgres 둘 다에서 돌린다.
  - 되돌릴 수 없으면(`migrate.IRREVERSIBLE`): 백업 성공을 조건으로 건다, `DEPLOY.md`에 업데이트 주의를 적는다, 끝 보고에 크게 적는다.
  - 내리면 다시 못 만드는 기록이 사라지면(`migrate.DATA_ON_DOWNGRADE`): 그 내리기는 백업 성공을 조건으로 건다.
  - 옛 이미지는 모르는 리비전이 찍힌 DB로도 뜬다(0.42.0부터). 이 성질을 깨는 리비전(칸을 바꾸거나 지우기)이면 `DEPLOY.md` 9-2에 적는다.
- **옛 화면 ↔ 새 서버, 새 화면 ↔ 옛 서버**
  - 응답 필드는 **더하기만** 한다. 빼거나 뜻을 바꾸지 않는다. 시작 때 떠 둔 API 모양과 끝의 것을 비교해, 빠진 경로·필드가 0인지 본다.
  - 화면은 서버가 새 필드를 안 보내도 깨지지 않게 한다. 옛 모양의 응답을 넣는 화면 테스트로 확인한다.
  - 요청에 새 필드를 더하면 서버는 그 필드가 없어도 받는다(옛 화면이 보낸다).
  - 서버가 보내는 문자열(이유·코드)을 화면에서 다른 말로 보이게 바꿀 때는 **서버 문자열은 그대로 두고 화면에서 바꾼다.**
- **새 입력의 한도**: 사용자가 보내는 새 값(설정·문자열·목록)은 크기·범위를 서버가 검사한다. 사람 수만큼 곱해지는 새 외부 호출에는 한도를 건다(기존 한도는 `services/limits.py`).
- **이름**: 이미 띄운 서버의 설정·쿠키·저장 키 이름은 바꾸지 않는다.
- **배포는 주인이 한다.** 총괄은 PR을 만들고(§2 라운드 끝), 끝 보고에 주인이 할 순서·주의·되돌리는 법을 적는다.
- **가짜 서버**
  - 새 바깥 접점이나 새 화면 상태(새 설정, 새 오류, 새 기록)가 생기면 `devtools` 데모 데이터에도 넣는다.
  - `tests/test_devtools.py`가 통과해야 한다.
- **방침**: 수집하는 것이 늘면 개인정보처리방침·이용약관을 같이 고친다(`lib/policy.ts`의 시행일 포함).

## 운영 방식 — 누가 어느 역할을 맡나

| 역할 | 누가 | 이유 |
| --- | --- | --- |
| 기획자 · 실행자 | 총괄 | 주인과 이야기하고, 맥락을 이어 구현한다 |
| 계획 검토 — 개발자·검토자·사용자 | **새 서브 에이전트 셋**, 동시에, 읽기만 | 계획 단계에서 잡으면 문장만 고치면 된다 |
| 검토자 | **새 서브 에이전트** `round-reviewer`, 자기 git worktree | 만든 사람의 생각을 모르는 눈. 뮤테이션은 파일을 고치므로 작업 트리를 나눈다 |
| 사용자 | **새 서브 에이전트** `round-user`, 전용 포트 | 코드를 모르고 화면만 보는 눈 |

- **언제 부르나**
  - 계획 검토: 라운드 크기 "중간·큼", 또는 마이그레이션·규제 영향이 있는 라운드. "작음"이고 둘 다 없으면 건너뛴다(§1 6단계).
  - 개발 뒤 검토자·사용자: 크기 "중간·큼" 항목은 항목마다, "작음" 항목들은 묶어서 한 번. 라운드 끝에 전체 회귀·호환을 보는 검토를 한 번 더 한다.
  - 검토자·사용자는 **백그라운드로** 띄우고 다음 항목을 진행해도 된다. 판정이 오기 전에 결과를 짐작해 적지 않는다.
- **검토자에게 넘기는 것**:
  - 항목의 완료 조건
  - 커밋 범위와 **라운드 시작 커밋**, 시작 때 떠 둔 기준 두 가지의 경로
  - 규제 영향 항목에 대한 주인의 결정(`status.md`)
  - 이 라운드의 `RULES.md`("지켜야 할 선"·"운영 중인 앱이라 생기는 규칙"·§3)
  - 앞 판정의 "조건부" 목록
  - 계획 검토 의견서 셋(`plan-*.md`) — 계획 때 나온 걱정이 풀렸는지부터 본다
- **검토자가 지키는 것**: 고치지 않는다. 커밋하지 않는다. 끝날 때 자기 worktree의 `git status`가 깨끗한지 확인한다.
- **사용자에게 넘기는 것**: 가짜 서버를 띄우는 명령과 전용 포트(위 "가짜 서버 다루기"), 이번 과업(§4), 스크린샷 둘 곳(저장소 밖).
- **사용자가 지키는 것**: 코드를 읽지 않는다. 띄운 서버는 **PID로** 끈다.
- **판정문**: 둘의 판정문은 총괄이 손대지 않고 라운드 폴더에 커밋한다(`<항목>-review.md`, `<항목>-user.md`).
- **불합격이면**: 총괄이 고친다 → **새** 검토자를 부르고, 이전 판정문을 넘긴다. 같은 항목이 세 번 불합격이면 주인에게 묻는다.
- **`status.md`**: 항목 시작·판정·주인 질문 때마다 고치고 **커밋·푸시**한다.
  - 적는 것: 상태(진행 중/끝), 항목과 체크, 마지막 판정, 남은 조건부, 주인 질문과 답, **다음 할 일(세션이 끊겨도 이 줄만 보고 이을 수 있게)**.
- `.claude/agents/`의 `round-reviewer`·`round-user`를 이름으로 부른다(없으면 만든다).
  - 계획 검토의 검토자·사용자 입장은 같은 정의에 "이번엔 계획 검토 — 읽기만, §1 6단계 형식으로"를 붙여 부른다. 개발자 입장은 일반 에이전트로 부른다.
  - 계획 검토의 사용자 입장도 화면을 띄우면 개발 뒤 사용자와 같은 규칙(전용 포트, PID로 끄기)을 따른다.

**실행 환경에서 못 하는 것** — 우회하지 않고 대신할 길:
- 바깥 인터넷: 가짜 서버로 확인한다. 실제 출처는 주인이 `diagnose.bat`·`verify.bat`로 본다.
- Docker: CI가 확인한다.
- 아이폰 사파리·실기기 알림: 주인 확인 목록으로 넘긴다.
- 갤럭시 크롬: Playwright 폰 360px로 대신 본다(브라우저는 `/opt/pw-browsers/chromium`에 있다 — 내려받지 않는다).
- 조직 정책 거부(403·407): 재시도·우회하지 않고 보고한다.
- 주인이 막은 도구 호출: 같은 것을 다시 시도하지 않고 멈춰 묻는다.

## 1. 기획자 (총괄)

**할 일: 이번 라운드에 무엇을 할지 정하고, 주인 승인 ①을 받는다.**

1. **지금 상태 확인** — §0을 읽고 잰 것을 `status.md`에 적는다. 시작 수치와 기준 두 가지를 뜬다.
   `ROADMAP.md` 0-1에서 **주인이 할 일로 남은 것**(배포·규제 확인 등)을 옮겨 둔다 — 이번 라운드에 걸리는 것이 있으면 계획에 적는다.
2. **요청 정리** — 주인 요청마다 네 방향 중 어디인지, 그리고 개발/디자인 중 어디인지(위 "개발과 디자인의 경계") 적는다.
   요청이 비었으면 `ROADMAP.md` 0-1 "다음 라운드 후보"와 아래 씨앗 목록에서 3~5개를 고른다. 주인이 쓰는 모습에 가까운 것부터.
   **이미 한 것은 빼고**(ROADMAP 11장·README에서 확인). 주인 요청이 모호하면 주인 말을 바꿔 쓰지 말고 해석 두세 가지를 보기로 묻는다
   (9-13에서 "맨 끝"을 잘못 읽은 일이 있었다). 주인이 "이건 나중에 해야 하나?"처럼 물으면 그것도 보기로 답한다.
3. **항목마다 적는 것**:
   - 무엇(주인 말로 한 줄) · 왜 · 크기(작음·중간·큼)
   - 규제 영향(없음 / 있음 → 무엇)
   - 데이터: 새 테이블·컬럼인가 · 공용인가 사용자별인가 · **다시 만들 수 있나** · 마이그레이션이 되돌릴 수 있나
   - 외부 호출이 느는가(사람 수만큼 곱해지는가)
   - 화면 말이 바뀌는가(→ 용어집)
   - 부딪히는 기존 결정(ROADMAP의 절 번호)
   - 되돌리는 법(스위치·기본값)
   - 완료 조건(검토자가 그대로 확인할 수 있게)
4. **순서** — 주인 요청이 먼저다. 다만 기록을 시작해야 하는 것(다시 못 만드는 것)이 관련되면 "지금 시작하지 않으면 그 전 기록은 영영 없다"를 맨 위에 적어 주인이 정하게 한다.
5. **크기 맞추기** — 라운드 크기를 넘으면 나눠서 다음 라운드 후보로 남긴다.
6. **계획 검토 — 세 입장이 한 번씩** ("언제 부르나"에 해당할 때만)
   - 1~5로 쓴 초안을 라운드 폴더 `plan-draft.md`로 저장·커밋하고, 서브 에이전트 셋을 **동시에** 부른다. 셋 다 읽기만 한다.

     | 입장 | 보는 것 | 읽을 것 |
     | --- | --- | --- |
     | 개발자 | 정말 만들 수 있나 · 크기가 맞나 · 마이그레이션·호환 · 지금 코드와 부딪히는 곳(파일:줄) · 더 작은 길 | 초안 + 관련 코드·테스트 |
     | 검토자 | 규제 영향 · 데이터 경계 · 보안·입력 한도 · 외부 호출 · 되돌릴 수 있나 · 확인 방법이 있나 | 초안 + "지켜야 할 선"·"운영 중인 앱이라 생기는 규칙" + 관련 코드 |
     | 사용자 | 주인 요청을 제대로 읽었나(원문과 대조) · 정말 필요한가 · 설명 없이 찾을 수 있나 · 말이 쉬운가 · 매일 쓰는 흐름을 방해하나 | 초안 + 주인 원문 + 가짜 서버 화면(코드는 읽지 않음) |

   - **형식은 하나**: 항목마다 `찬성 / 걱정 / 제안`, 걱정마다 심각도(막음·고쳐야 함·참고)와 근거. 한 사람에 한 쪽 안.
     파일은 `plan-dev.md`·`plan-review.md`·`plan-user.md` — 총괄이 손대지 않고 커밋한다.
   - **한 번만 돈다.** 총괄은 걱정마다 `반영 / 반영 안 함(이유) / 주인에게`로 답을 적어 최종 계획 `plan.md`를 만든다.
   - **다시 묻는 건 딱 하나의 경우**: 반영하면서 항목을 바꾸거나 새로 넣었으면, 그 **바뀐 부분만** 그 걱정을 낸 입장에게 한 번 더 보인다(`plan-recheck.md`).
   - **"막음" 걱정을 "반영 안 함"으로 넘기지 않는다** — 고치거나, 주인에게 올린다.
   - 셋의 의견이 갈리면 총괄이 대신 정하지 않는다. **이견** 칸에 양쪽 이유를 그대로 두고 주인에게 보기로 올린다.
7. **주인에게** — 최종 계획(항목 표) + **이견**(보기 2~4개 + 추천) + 반영 안 한 걱정과 그 이유 + 고를 것.
   규제 영향이 있는 항목은 따로 묶어 보인다. 화면 말이 바뀌는 항목은 **바뀌기 전·후 문구**를 보인다. 계획 검토를 건너뛰었으면 그렇다고 적는다.

### 씨앗 목록 — 요청도 ROADMAP 후보도 비었을 때만

살아 있는 목록은 `ROADMAP.md` 0-1 "다음 라운드 후보"다. 이 목록은 그것이 비었을 때의 씨앗이고, 실제 코드·ROADMAP 11장과 대조해 이미 한 것은 빼고 쓴다.
*(이미 한 것: 시그널 규칙을 한 곳으로 0.41 · 시그널 기준 내 설정 0.42 · 날마다의 평가금액 기록 시작 0.44)*

- **고도화**: 백업을 서버 밖으로 자동으로 꺼내기 · 느린 요청 기록에서 실제로 느린 곳 고치기(주인 서버의 기록 필요) ·
  시세 제공자가 막힌 날 대비(주인에게 실패 푸시, 진단 화면에 제공자 상태) · 알림 조용한 시간·종목별 끄기·하루 요약 · 앱스토어(보류, 주인 결정)
- **정교화**: 시그널 임계값의 근거 복원(저장된 시세로 발동 빈도와 그 뒤 N일 움직임 분포를 재는 **내부 보고서**, 주인 전용 — 화면에 수익률로 보이면 규제 영향) ·
  데이터 품질 자동 점검(제공자 간 종가 대조, 분할 누락·급변, 공시 시점 — `verify.bat`를 매일) · 주문 가이드 정밀도(반올림 방향, 최소 거래 단위, 환율 시점) ·
  오류·경계 문구 정리
- **전문화**: 거래 내역 기록 시작(다시 못 만든다) · 위험 지표(변동성·최대 낙폭·상관·실질 종목 수·통화·시장 노출) ·
  성과(기간·시간가중 — 평가금액 기록이 쌓인 뒤, 남과 비교·광고하지 않는다) · 리밸런싱 시뮬레이션(저장 없이 미리 보기) · 세금·수수료(주인 결정)
- **사용자화**: 첫 화면 탭 고르기, 대시보드 칸 고르기·순서 · 알림 종류·시간 개인 설정 · AI 요청 서식 여러 개 저장

## 2. 실행자 (총괄)

**항목마다**:
1. `status.md`에 그 항목의 작업 목록을 적는다.
2. 서버 → 화면 → 가짜 서버 데모 → 문서 순으로 만든다. 커밋은 작게 나누고, 푸시마다 CI를 확인한다.
3. 확인한다:
   - 단위 테스트 · 경계값
   - **뮤테이션** — 핵심 줄 10개 안팎을 되돌려 테스트가 잡는지 본다. 결과는 라운드 폴더 `<항목>-mutation.md`로.
   - 마이그레이션 두 DB
   - 격리 표
   - 화면 문구를 바꿨으면: 옛 문구가 테스트·용어집·README에 남았는지 `grep`
   - 브라우저 — **빌드한 뒤** PC 1400 · 폰 390/360 × 다크·라이트. 가로 넘침·잘린 글자·44px·대비·콘솔 오류.
4. 검토자·사용자를 부른다(운영 방식).

**라운드 끝에**:
- **버전**: `backend/app/version.py`에 한 줄 설명을 달고 `APP_VERSION`을 올린다. 기능이 늘면 0.x.0, 고치기·다듬기만이면 0.x.y.
- **ROADMAP**:
  - 단계 기록을 **11장 "키우기 라운드"** 아래 `11-N`으로 이어 적는다(10장은 디자인 다듬기다). 한 것, 계획과 달라진 것, 정한 것과 이유.
  - 0-1 "지금 남은 것"과 **"다음 라운드 후보"**를 고친다(이번에 나눠 미룬 것 + 하면서 보인 것, 네 방향으로. 디자인 후보는 따로).
- **README**: "화면 구성"에 버전별 항목을 더한다.
- **바꿨다면 같이 고칠 것**: 명세(시그널), `DEPLOY.md`(배포), 방침(수집 항목), 용어집(화면 말).
- **시작 수치와 비교**: 테스트 수가 줄지 않고, lint 경고가 늘지 않는다. 전체 테스트 출력은 저장소 밖 파일로 두고, 보고에 경로를 적는다.
- **`status.md`**: 상태를 "끝"으로 바꾸고 커밋·푸시한다. 그래야 다음 라운드가 이 라운드를 이어 붙잡지 않는다.
- **PR 만들기** — 주인은 깃허브의 Merge 버튼으로 합친다. 서버는 기본 브랜치의 `latest` 이미지를 받으므로 **합치기 전에는 배포되지 않는다.**
  - 작업 브랜치 → 기본 브랜치로 PR을 연다(PR 양식 파일이 있으면 그 절을 따른다). 제목: `<버전> <라운드 이름>`.
  - 본문: 한 일(항목마다 한두 줄) · 마이그레이션과 되돌릴 수 있는지 · 새 `.env` 이름(값은 적지 않는다) · 라운드 폴더 링크.
  - PR 소식(CI·리뷰)을 받도록 구독하고, CI가 초록이 될 때까지 고친다. 빨간 PR을 주인에게 넘기지 않는다.
  - 기본 브랜치가 그새 앞서 나가 충돌이 나면 기본 브랜치를 작업 브랜치에 **합쳐서**(rebase 아님) 풀고 다시 확인한다.

## 3. 검토자 (항목마다 새 서브 에이전트)

실행자의 보고를 믿지 않고 직접 돌린다. 해당 없는 칸은 "해당 없음"이라고 적는다.

| 검사 | 방법 | 합격 |
| --- | --- | --- |
| 완료 조건 | 기획 표의 그 항목 | 전부 |
| 계획 때 걱정 | `plan-*.md`의 걱정 중 "반영"으로 답한 것이 실제로 반영됐는지, "막음"이 남아 있지 않은지 | 전부 반영, 막음 0 |
| **회귀** | 전체 테스트 + 시작 수치와 비교. 새 설정을 켜지 않은 상태에서 시작 때 떠 둔 **응답 사진과 같은지**(날짜·시각 필드 제외, 새로 더한 필드 제외) | 줄어든 테스트 0, 달라진 값 0 |

## 4. 사용자 (항목마다 새 서브 에이전트)

코드를 읽지 않고, 가짜 서버 화면으로만 써 본다.

| 사람 | 데모 계정 | 보는 것 |
| --- | --- | --- |
| 주인 (PC·아이폰, 매일) | `owner@example.com` | 새 기능이 매일 보는 흐름을 방해하지 않는지 |
| 지인 (갤럭시만, 주식 초보) | `friend@example.com` | 새 기능을 설명 없이 찾고 이해하는지. 새 용어에 풀이가 있는지 |
| 처음 온 사람 | `new@example.com` | 종목 0개에서 새 기능이 어떻게 보이는지 |
| 승인 대기 · 손님 | `pending@example.com` · 로그인 안 함 | 새 기능이 새어 보이지 않는지 |

**과업**
- **이번 과업**: 기획자가 항목마다 1~3개를 정한다. 사용자의 말로 쓴다. 예: "내 ADX 기준을 25로 바꾸고, 오늘 매수 시그널이 몇 개로 바뀌는지 본다".
- **회귀 과업**: 매번 걷는다.
  1. 오늘 매수 시그널이 뜬 종목을 찾아 차트에서 그 날을 확인한다
  2. 새로 넣을 돈 100만 원으로 주문 가이드를 받는다
  3. 여러 종목의 수량·평단가를 한 번에 고친다
  4. 금액을 가리고 손익 %만 본다
  5. 폰 뒤로가기로 팝업을 닫는다
- **사용자화 항목이 있으면 더 걷는다**: 설정을 바꿨다가 **기본값으로 되돌리기** — 되돌리는 길을 설명 없이 찾는지, 되돌린 뒤 화면이 처음과 같은지. 바꾼 설정이 어디에 쓰이고 있는지(내 기준인지 기본인지) 화면에서 알 수 있는지.

**그 밖의 조건**: 상승 색 빨강 · 확대 150%(창 933px, 배율 1.5) · 아주 긴 종목명 · 억 단위 금액

**결과**
- "막힌 곳 / 헷갈린 말 / 찾지 못한 것 / 좋았던 것" 표로 낸다.
- 줄마다 사람·과업·스크린샷 경로·심각도(못 끝냄 / 헤맴 / 거슬림)를 적는다.
- 고칠 방법은 적지 않는다.

## 5. 합격 기준

- 모든 항목이 검토 합격이고 조건부가 비어 있다. CI 두 갈래가 초록이다.
- 시작 수치보다 테스트 수가 줄지 않고, lint 경고가 늘지 않는다.
- 새 기능을 켜지 않으면 이전 버전과 같은 결과가 나온다.
- 옛 화면·새 서버, 새 화면·옛 서버 어느 쪽도 깨지지 않는다.
- 이번 과업과 회귀 과업에 "못 끝냄"이 없다.
- 문서(README·ROADMAP·version.py, 바뀌었다면 명세·DEPLOY·방침·용어집)가 코드와 맞는다.
- `status.md`가 "끝"이고 푸시돼 있다. PR이 열려 있고 CI가 초록이다.

## 6. 끝 보고 (총괄 → 주인)

주인은 개발자가 아니다. 명령은 그대로 복사해 붙일 수 있게, 나머지는 결과로 말한다.

- **한 일**: 항목마다 2~3줄 · 버전·PR 링크 · 정한 것과 이유
- **숫자**: 시작 → 끝(테스트 수, lint, 성능) · 뮤테이션 결과
- **판정**: 검토·사용자 판정 요약(파일 링크), 고친 것과 남긴 것
- **스크린샷**: PC·폰, 두 테마. 전후.
- **배포 안내** — 주인이 하는 순서 그대로:
  1. 배포 전 손으로 백업을 떠 둘지(마이그레이션이 있으면 대개 "예" — `DEPLOY.md` 10)
  2. PR 링크를 열어 **Merge** 를 누른다
  3. 깃허브 Actions의 "Docker 이미지"가 초록이 될 때까지 기다린다(몇 분)
  4. 서버에서 `DEPLOY.md` 9번의 한 줄을 실행한다 — 그 줄을 보고에 그대로 적는다. 새로 넣을 `.env`가 있으면 이름만 적고 값은 적지 않는다
  5. 화면 오른쪽 위 버전이 새 버전인지 본다
  - 마이그레이션이 있는가, 되돌릴 수 있는가
  - 배포 뒤 확인할 것
  - 되돌리는 법
- **주인 확인 목록**: 아이폰·갤럭시 실기기 · 실제 시세(`diagnose`·`verify`) · 실제 AI 키 · 규제 영향 항목에 대한 결정
- **다음 라운드 후보**: `ROADMAP.md` 0-1에 적은 것을 네 방향으로 묶어 보인다(디자인 후보는 따로).
- **며칠 써 보고 알려 줄 것**: 이번에 바뀐 곳 중 주인이 실제로 써 보며 느낌을 봐야 하는 자리 두세 개. 다음 라운드의 "쓰면서 불편한 점" 칸으로 이어진다.
